# 0035. Component properties and overrides, as Figma has them

- Status: proposed
- Date: 2026-11-17 (amended the same day after review: item 3's values have an identity on the instance; amended again after the second review: each value is written, undone and merged on its own, item 15; amended a third time on 2026-11-18 after the third review: the record is the only place a value is, and driven layers show it as they're read, items 3, 14 to 18; amended a fourth time the same day after the fourth review: the record wins over a stale layer at every boundary, detach hands on inherited values, a record two people make at once merges field by field, and a tab from before records keeps its unsent edits, items 3 and 15; amended a fifth time the same day after the fifth review: a record that exists decides every key, a tab from before records only views the file, its safe queued edits applying, and a delayed rebuild can't store a copy reference into a main its layer left, items 3 and 15; amended a sixth time on 2026-11-19 after the sixth review: no instance without a record reaches a client (the room migrates a stored file once, every path content comes in by folds it, and the room refuses an edit leaving one without), merges compare a record's presence, copy references are derived top-down by origin, and a socket that doesn't say its protocol is an old tab's, items 3 and 15)
- Deciders: Ziyang (lead maintainer)

## Context

A 500k-layer commercial UI kit imported from a `.fig` (decision 0030) shows how far instances are from Figma's.

- **Properties.** Figma's Button has seven: Variant, State and Size (variants), Show Left Icon, Show Right Icon and Show KbdGroup (booleans) and Button Text (text). Drawpane shows the three variants only. Figma's Field has Orientation, Data Invalid and Description Placement (variants), Label, Description and Link (booleans), Label Text and Description Text (texts), Input Type (an instance swap), and, under a "Textarea" heading, the State and Placeholder Text of the nested Textarea instance, which Field exposes. Drawpane has variants and nothing else: no booleans, texts or swaps, no exposed nested instances. The importer drops `componentPropertyDefinitions` and notes "component-properties".
- **Overrides.** Drawpane lists every overridden property by its internal name. The Button lists nine: `Instance · radius, effects, height, minHeight, variantProps, width` and `Button · position, width, text`. Figma counts one change there: the text. The Field lists more than twenty (`Textarea · alignItems, gap, height, instanceOf, layoutMode …`).

Where the noise comes from, measured on the kit (503,466 nodes, 20,513 instances; the converter's output before `pinInstances`, then after):

| Marked overridden | Converted | Pinned | Why |
| --- | --- | --- | --- |
| `variantProps` on instances | 0 | 14,506 roots, 4,384 nested | Sync copies a variant's `variantProps` onto its instances, so `pinInstances` pins the instances that don't have it. It describes the main, like `componentDescription`, and no instance should hold it. |
| `width`, `height` on roots | 13,939, 9,037 | 11,887, 7,648 | The converter compares a root's size with its main's. Most of these roots hug or fill (`inst=hug main=hug`, `inst=fill main=fixed`), so layout decides their size. |
| `sizingH`, `sizingV` on roots | 7,411, 1,351 | 6,558, 677 | Fill is how an instance sits in its parent (Figma's `layoutGrow`, `layoutAlign`), so it belongs to the instance like its position. |
| `x`, `y`, `width`, `height` inside copies | 26,236, 18,873, 51,689, 29,409 | 24,646, 16,943, 52,619, 32,448 | Layers placed by auto layout, sized by hug or fill, auto-sized text, and children moved or stretched by their constraints in a frame the copy resized. Figma saves these laid out (`derivedSymbolData`, #171) and doesn't count them as overrides. |

Sync (`syncInstanceOps`) already leaves some layout-decided values alone, but only a nested layer's position and size in auto layout, hug sizes and auto-sized text, decided from the main's values. The converter's `markOverrides` checks none of it. `pinInstances` pins whatever sync would still change, so anything sync misses becomes an override.

What's left after that is real in Drawpane's model: a resized instance, a changed fill, a swapped icon. One kind isn't real in Figma: copies in a frame set to another variable mode differ in fills and strokes because the import stores each layer's resolved value. Decision 0034 makes those bindings resolved in the view, so the differences go away there, not here.

## Decision

### Properties

1. **Definitions.** A main component, or a component set for its variants, defines its properties in `componentProps`: an ordered list, at most 64, each with
   - `id`: stable, so renaming keeps every reference;
   - `name` (at most 64 characters), `description` (at most 500);
   - `type`: `variant`, `boolean`, `text`, `instance` (instance swap) or `slot`;
   - `default`: a boolean, a text (at most 10,000 characters) or a component id;
   - `preferred`, for an instance swap: component or set ids, at most 64, in order.

   A variant's values stay in its variants' `variantProps` (they decide which variant an instance is). Its entry in `componentProps` gives it its place in the order and its description. A set without entries for its variants shows them first, as now.
2. **References.** A layer says which of its values a property drives in `propRefs`: `{ visible?, characters?, instanceOf?, slot? }`, each a property id. A boolean drives `visible`, a text `characters`, an instance swap a nested instance's `instanceOf`, a slot a frame's content (decision 0032). One property may drive several layers.
3. **Values belong to the instance, by property id, in one place.** An instance holds the values it sets in its record, `propValues`, keyed by property id: `true` or `false` for a boolean, a text for a text, `{ instance: componentId }` for an instance swap. A key that isn't there means the instance takes what its main gives: the property's default, or, for a nested instance, what the main around it set. The record is the only place a value is kept. A layer a property drives (one whose `propRefs` names it, in the instance's copy, down to but not inside nested instances) shows the record's value for its key, or its main layer's value when the record has none, worked out where the layer is read: never stored on the layer as an override. It's decision 0034's rule, "store what's bound, resolve it where it's read", and the way compact copies present a copy's layers (decision 0029).

   - **Where nested instances' values are.** Only an instance that isn't itself a copy has a record: a top-level instance, or a nested instance in a main. A nested instance inside a copy keeps its values in the record of the instance it's ultimately in, under its **scope**: `scope/propertyId`, the scope being the ids of the main layers each nested instance on the way down copies (`ownLayerId`: follow `mirrors` to a layer a main holds itself). Those are ids of layers mains hold, never copies' ids, so a key reads the same in either copy form and a conversion keeps it. A key's scope is at most 32 nested instances deep (`PropertyKey`). So setting a nested instance's first value writes one entry of a record that already exists: there's no record to make, and two people's first values can't both try to make it.
   - **Where it's read.** Compact copies: `CopyView` presents a copy layer's driven fields from its instance's record when it builds the layer (`drivenRefs`, `applyPropertyValues`), whatever the layer's own record holds for them, and a nested instance a swap property drives is presented as an instance of the component the record chose. It keeps, per built instance, which copy layers each key drives, so changing one value forgets only the layers it drives (a swap's rebuilds that instance). The room's readers use the same `CopyView`, so they read what editors show. Materialized copies (`COMPACT_COPIES=off`, a file not converted yet): sync builds a copy from its main and its overrides, and now from the record too: a driven field takes the record's value or its main layer's, a swap property's nested instance is built from the chosen component (`syncInstanceOps`). It's a pure function of the main, the record and the copy's other overrides, so every client that syncs an instance writes the same; there's nothing to reconcile afterwards. Setting a value in that form writes the record and syncs the instance's driven fields and structure in the same transaction (`syncInstanceOps` with `properties`). One window is left, the same as for any value a main gives its materialized copies: an edit synced from a file without a teammate's concurrent edit (a layer added to the main while a value was set, a variant switch while a value was set, a branch merge taking the record from one side and a layer from the other) leaves that layer showing its main's value until the instance syncs again, at its next property edit or its main's next edit. The record has the value everywhere meanwhile, every client and the room hold the same file, and compact copies (the default, and what every room converts to) have no such window. A layer that differs from its record only because it's stale this way is never taken for a value of its own: wherever the instance's link ends or changes form, the record wins. One model function says what a driven field shows there (`drivenShown`), and conversion, detach and unlink all use it, so they agree: the record's value for the key; when the instance keeps a record without the key (a reset, or a value never set), the main layer's; when it keeps no record, the layer's own (below). A swap is a driven field like the others: a nested instance a stale swap left is detached as an instance of the component the record chose, its layers that component's, unlinked keeping it as its own swap, and converted from it (`shownValues`, `recordWins`, `staleSwap`, review 5, P1 #1 and #2). Conversion never detaches an instance for staleness (review 4, P1 #4).
   - **A record that exists decides every key.** Every instance that isn't a copy keeps a record (`propValues`, empty or not, `hasRecord`): a key it doesn't keep means the main's value, wherever it's read. Removing the last key leaves an empty record (`{}`), not none. An instance from before records (its values on its layers: a materialized file from this pull request's earlier heads, a version saved before, a paste or a library from before) has every value its layers show folded into a record once, by one model function (`foldRecord`, `migrateRecords`), before any client reads it. It keeps every value or unlinks: a key takes the first layer, in layer order, that shows another value than its main layer's; a layer of the same key showing something else, or a value past the record's bounds, is unlinked from its property and keeps what it shows as an override, as the import always did. Nothing is dropped (review 6, finding 6).
     - *Why a migration, not data that describes itself.* The alternative was weighed first (after #186's migration review): a key the record keeps decides, an absent key leaves a legacy layer value in effect as that layer's own override until a new-code edit or reset writes the key and clears the key's legacy overrides in the same transaction, with nothing ever knowing whether an instance was "migrated". It can't represent a variant switch (or an instance swap) of an instance whose driven layer still holds a legacy value without losing data: the switch makes new layers, so the value is dropped (lost), carried onto the new layers as an override (a teammate's concurrent reset of that key is then brought back: the reset cleared the old layers, the key is absent, the carried value shows), or written as the key from the switching client's view (a teammate's concurrent first edit of the key is then overwritten by a value nobody set). Only a durable per-key "reset to the main's" value, written by every reset and never removed, closes the second, and that is a marker again, in a new kind of value every reader of a record would have to handle. So the file migrates, once, and is held to the bar #186's review set for migrations: a version saved first; the marker written in the same storage transaction as the last instances folded, in bounded steps that resume (and fold only instances still without a record, so a step run twice changes nothing); no ids made (the fold writes records and layer fields only); a branch, its base and main each folded by the same deterministic function, so an instance nobody changed merges as no change; clients never migrate stored data (they fold only content they're about to write, a paste or a library's components, with the same function, and the room refuses content that isn't); every snapshot or log a client loads after it holds the migration as the edits it made (they're logged), so nothing is replayed across it unconverted; and every path content comes in by folds it (below), each tested.
     - The room migrates its stored file when it loads (`#migrateRecords`, the conversion's pattern, decision 0029): a version first ("Before component properties"), then a step of instances at a time, each a transaction logged and sent to everyone, the marker written with the last; before compact conversion, which reads records. While it's under way, an edit reaching an instance not migrated yet has that instance folded first, so the edit lands on its record.
     - Every other way content comes in folds it before it's written: an import (`.fig`, Figma link and Penpot through `pinInstances`, and again as the room commits the staged nodes), a duplicate or a template (the room's import of a snapshot), a paste (against the file it's pasted into), a library's insert and update (its publish folded), a restored version or branch version (folded as it's loaded), and both sides of a branch merge or an update from main, base included, so they compare records.
     - Clients never fold: the editor's first-record fold is gone, and the room refuses, saying so, an edit that would leave an instance without a record (one made without one, a frame made an instance without one, a record removed). The editor makes every instance with an empty record. Without that, two clients each folding a file from before records from their own view overwrote each other's acknowledged values, and a fold that couldn't fit dropped values (review 6, findings 1 and 6).
   - **Direct edits.** Editing a field a property drives by hand inside an instance (typing in the label, hiding the icon, swapping the nested instance) is an edit of the property: it becomes a keyed set of the record its value is in (`drivenEditOps`), and every layer the property drives shows it. A reset deletes the key: the layers show their main layer's value again, with its variable binding and text runs, because those were only hidden while the record had a value. Detaching an instance materializes what its layers show into plain layers, and gives each nested instance inside it, now an instance on its own, every value it shows: those its outer record held for it, scope taken off, over those its main layer's own record holds (what the main around it set, which it showed where the outer record had nothing), while it's an instance of that layer's component (`nestedValues`, review 4, P1 #3). In materialized copies its layers then copy its own component's layers, one step down the copy chain, so it follows that component and converts. Copy references are derived top-down by origin, a pure function of the file a transaction leaves (`resolveUnder`, in the model's `applyTransaction`, so the room, every client and replay agree): each layer under an instance copies a child of what its parent copies (the parent's main layer for a copy, its main for an instance root following one, the component it's swapped to for a swapped nested instance). A layer whose reference isn't one of those children is pointed at the child whose copy chain ends at the same main layer (its origin): through to the inner component after a detach, back to the outer copy when the detach is undone. Parents come before children, over the layers a transaction made and those under every node whose link it changed; a layer no child matches is left, for conversion to report. Repairing child-first, or only following a reference downwards, left references a level deeper, and after an undone detach, pointing into a main their instance no longer follows (review 5, P2 #7; review 6, findings 3 and 4). Unlinking a layer from a property (its `propRefs` no longer naming it) keeps what it showed, as its own value. Operations in one transaction are read in order, each against the references the ones before it leave: a layer unlinked and then edited in one change (an agent's `set_props` with both, which puts references first) gets the edit as its own value, and the property's other layers keep theirs; an edit before the unlink is the property's, and the layer keeps it (review 4, P2 #5).
   - **Lifetime.** A key lasts until it's reset (its row's reset, or Reset all, which clears every key under the instance's scope), the instance is detached, or it switches to a component outside its set that doesn't define the property. Switching variants keeps every key the set defines, whether or not the new variant has a layer that takes it, so a round trip through a variant without the label brings the label's text back. Keys are matched by id, never by layer name, so a label named differently in another variant takes the value. A layer that starts referencing the id (added to the main, linked to the property, rebuilt by a swap) shows the value as soon as it's read (compact) or synced (materialized). A key whose definition the main removes is dormant: not shown, not applied, and dropped at the instance's next switch.
   - **Nested instances across a switch.** Switching an instance changes the layers its copy has, and with them the scopes its nested instances are under. Their values go across (`carryOps`), matched as Figma matches them: a nested instance of the same component at the same layer path; then one of the same component, in layer order; then one at the same path (a component swapped meanwhile, whose values go by property id where it defines them). Every nested instance takes part in each pass, those that set nothing too, so an unchanged sibling keeps its exact match and another's values can't land on it (review 3, P2 #4). Nested instances inside a matched one go across in turn: the same component inside means the same layers, so their keys keep the rest of their scope. A swap property's change carries what's set inside the nested instances it swaps the same way, and a value whose nested instance has no match goes.
   - **Bounds.** A record holds at most 512 keys (its own properties, 64 per set and per variant, and its nested instances'), each text bounded as a text layer's `characters` is (200,000), and at most 400,000 characters in all, keys included (`MAX_PROPERTY_VALUES_CHARS`): a record, and an operation that creates the node holding it (a paste, an undone delete, a branch merge), stay well inside the room's 4 MB message, as does each value's own write. The bounds are checked on what a transaction leaves (`checkKeyedMaps`), not after each operation, so the edits in one may pass through a larger record on the way (one value grows before another shrinks), and merging a client's unsent edits never turns valid edits into a transaction the room refuses (review 3, P2 #6). A value that doesn't fit isn't set: the record is the only place it could be, so the edit is refused with a notice, and nothing else changes.
   - **Precedence.** The instance's value comes before its main's default and before what the main around a nested instance set (a nested instance's own record, which the copy shows where the outer record has nothing). A field no property drives is an ordinary override, as before. Finding a property's layers for the panel reads an index kept until layers are added, removed, moved or relinked (`drivenLayers`, kept by `Doc.structure`, which a teammate's unlink in compact copies, a stored `unset`, moves too: review 3, P2 #5); typing in a driven text reads the layer and its instance, not the instance's copy.
   - **Swapped nested instances.** A nested instance swapped for another component takes that component's values, except where it sits (its root-local values) and the fields the outer component's properties drive: those stay the outer main's, shown with the outer record's values. Swapping the icon doesn't show an icon a boolean hides.
   - **Resets restore what a value depends on.** Resetting a property removes its key, so each layer it drives shows its main layer's state for that field again: the value, the variable bound to it, the runs of a text. Resetting an ordinary override restores the value and what it depends on from what the layer follows for that field, as sync decides it: for a swapped nested instance, the component it's swapped to, except its root-local fields and those the outer component's properties drive. Resetting a swap rebuilds the nested instance's layers from the component it goes back to. Resetting one variant axis puts that axis back and keeps the others' current values: the instance switches to the variant that has them, and stays changed while any axis differs.
   - **Several layers, one value.** A property that drives several layers has one value, and its layers can't show two: they all read the same key. A layer meant to differ is unlinked from the property (its references don't name it), and keeps its own value; an import unlinks a copy's layer that shows another value than the one its property takes (item 14), and keeps one Figma lists as unlinked.

   *Why this replaces the first two choices.* Phase 1 kept a value only on the layers it drives. The first review showed that holds only while the instance's layers stay the same: a variant switch carried overrides by layer name, so a label named differently lost its text; a round trip through a variant without the label lost it; a boolean driving two layers showed `false` while its layers were `[false, true]` once the main added the second. The first amendment added the record and kept the values on the layers too, so nothing that reads layers would change, with a client-side step making the layers agree after a teammate's edit. That was two stores of one value. Three rounds of review kept finding P1s in the space between them, each a schedule the reconciling step couldn't settle: concurrent edits leaving the record and the canvas apart, a reset that couldn't reach a layer its author hadn't seen, a delayed repair from an offline client overwriting a newer value, two clients both creating a nested instance's first record, a peer's unlink missing the cache, an agent's write changing the record but not its layers, and, under it all, an older client reading a keyed set as the whole record. Each fix added a case to the reconciliation. With one store there's nothing to reconcile: what a layer shows is a function of the record and the main, worked out where it's read, and every client reading the same file reads the same. The reconciliation step is gone, and with it the "repair" transactions it sent.

   *Existing files.* Files on main never had property references (its importer dropped them), so no stored file outside this pull request's own test imports has driven values to fold. Files made elsewhere hold what an instance set on the layers a property drives; they're folded into records as they're imported (`foldPropertyValues`, in `pinInstances`, which every import runs): a layer showing another value than its main layer's has it recorded under its key, first in layer order, and isn't marked for it; another layer of the same property showing something else, or a value past the record's bounds, is unlinked instead and keeps what it shows as an override, so the file draws as it did. A materialized file whose layers hold values with no record (an import from the pull request's earlier heads into a room with compact copies off) has them folded as the room converts it to compact copies, an instance at a time, in the conversion's own bounded steps (`foldValue`); an instance whose layers disagree with each other is left detached, keeping what it draws, as any copy that doesn't match its main is. Compact files stored by those earlier heads (only on test instances) aren't migrated: import the file again.
4. **Defaults.** A main's layers hold its defaults: a boolean's layers are visible when its default is true. Changing a default on the main sets those layers, so instances that haven't changed it follow, as any main edit reaches them.
5. **Nested instances.** A nested instance in a main can expose its properties (`exposeProps`, Figma's `isExposedInstance`). An instance shows them under the nested instance's name, below its own, and through exposed instances inside it in turn. A nested instance that isn't exposed keeps its properties to itself, as in Figma.
6. **Renaming, reordering, removing.** Rename and reorder edit `componentProps`. References name ids, so they stay intact. Removing a property removes its references in the main, and its layers keep their current values.

### Overrides

7. **What an override is.** An override is a value a copy holds that layout wouldn't give it. Laid out means one of these:
   - for an instance root: its position, and on an axis where it or its main fills, its sizing and size;
   - a layer placed by its parent's auto layout: its position, and its size on an axis that hugs or fills;
   - a layer that hugs: its size on that axis;
   - auto-sized text: its width when it grows sideways, and its height unless its size is fixed;
   - a child of a frame without auto layout whose size differs from its main's: its position on an axis pinned to the end or centre, and its position and size on one that stretches or scales.

   One function (`laidOutProps` in `@drawpane/model`) decides it for the converter's `markOverrides` and for `pinInstances`: an import doesn't mark them. Sync and resets don't just leave them alone: a value layout derives from the main's is derived again. A child pinned to the end, centre, both edges or scaled, in a copy frame of another size, takes its main layer's place moved by the constraint (`constrainedValues`), when its main layer moves and when its override is reset. Values auto layout, hug and auto-sized text decide are left to the layout pass, which gives them again. Laid out values are stored as decision 0029 says ("laid out", not overridden).
8. **Link properties.** `variantProps` and `componentProps` describe a main, and `propValues` is what one instance set. Copies don't take them from their main's layers, in either form, like `componentDescription`, and a copy layer's override record never holds `propValues` (the model refuses it). `propRefs` and `exposeProps` are copied like any value.
9. **The overrides list** shows what changed, in words, grouped by layer, nested instances under their path ("Textarea › Placeholder"):
   - names a person uses: "Text", "Fill", "Stroke", "Hidden" or "Shown", "Size", "Position", "Corner radius", "Effects", "Swapped to Check";
   - values a property shows above aren't listed again: a property row shows its own changed mark and reset;
   - a reset per item, which resets that value on that layer only. Today's reset syncs the whole instance, which would also undo every laid out value in it;
   - "Reset all", which resets the instance's changes, those inside its nested instances included, as Figma's does.

### The instance panel

10. Like Figma's, one row per property in the definitions' order: a dropdown for a variant (a segmented control for up to three values; a switch when its values are true and false), a switch for a boolean, a text field for a text, a picker for an instance swap (its preferred values first, then the components it can swap to). A row that differs from its main has the component dot beside its label and a reset. Exposed nested instances follow, each under its name as a heading. Then the overrides list, then Swap and Detach.
11. **On a main or set:** the definitions, each with its type, default and description. They can be renamed (double-click), reordered (drag) and removed; "Add property" offers the types and, for a boolean, text or swap, links the selected layer. A layer in a main shows which property drives it, with a way to unlink it.

### Import

12. **REST** (`GET /v1/files/:key`): a component or set's `componentPropertyDefinitions` (keys are `name#id`, variants just `name`; `type`, `defaultValue`, `variantOptions`, `preferredValues` by component key); a layer's `componentPropertyReferences` (`visible`, `characters`, `mainComponent`); an instance's `isExposedInstance`. Keys map to ids of their own, the same every time the same file is imported. Preferred values name components by key, matched to the file's components, or dropped when they're in a library the import doesn't bring.
13. **`.fig`**: Open Pencil's scene graph has the same (`componentPropertyDefinitions`, `componentPropertyReferences`, `isExposedInstance`). `@drawpane/fig`'s adapter writes them in the REST shape, so one converter reads both.
14. **Instances' values** come in as records: a copy's layers have Figma's values, and an import folds those its properties drive into the record of the instance they're ultimately in, under their keys (item 3, "Existing files"), and marks the rest as overrides only where they differ by more than layout. A copy's layer that leaves `componentPropertyReferences` out takes its main layer's; one that lists them, an empty list included, keeps its own (`propRefs: {}` when empty), marked as an override like any difference, in both copy forms; one whose value disagrees with its property's (another of the property's layers, first in layer order, gave the record its value) is unlinked the same way. So a layer Figma has unlinked keeps its text when a property is set later. The REST case is covered by a constructed fixture; the `.fig` scene graph can't tell an empty list from none, so a `.fig` copy takes its main layer's references.

### Everything else

15. **Sync and undo.** Definitions and references are properties set by operations, so collaboration, undo, branches and merges treat them as any value. A record is a map whose values are each written on their own: a `set` operation with a `key` (`{ op: "set", id, prop: "propValues", key, value }`, the key a `PropertyKey`, `null` removing it) changes one value, and its inverse puts back that one value. `KEYED_PROPS` in the model lists the maps written this way; `propValues` is the only one.
   - **Different properties never conflict.** Two people setting different properties of one instance at once both keep theirs, nested instances' too, since they're entries of the same record; an edit replayed over a teammate's (sync's rebase, a reconnect) changes only its own value; undo puts back only the value it changed, so it never reverts a teammate's value of another property. Branches compare a record value by value (`changedFields` makes one change per key, `changeKey` names it `id:propValues:key`), so main changing one property and a branch another merge without a conflict, in the editor's review and in the room's SQL merge alike, a nested instance's first values included (review 3, P1 #3).
   - **The same property** resolves as any same-field edit: the later write wins, everywhere, and what every layer shows follows it, because they read it.
   - **Protocol 3.** A client from before keyed sets would read a keyed set as the whole record, and a value removed as all of them gone; its model refuses an operation naming `propRefs`, `propValues`, `componentProps` or `exposeProps`, so it can't keep what it doesn't see over what it does to an instance. `PROTOCOL_VERSION` is 3. A tab already open on version 2 runs code that can't change, and holds its unsent edits in memory only: closed to reload at once, it lost them (review 4, P1 #2). The fourth amendment kept it an editor and translated its edits; the fifth review showed that can't hold over an instance's lifecycle (its delete and undo, detach, real undo and duplicate restore or change what it doesn't see), so after this change it only views the file (`protocol2Refusal`, `forProtocol2Ops`, `forProtocol2Nodes` in the model):
     - it's welcomed as a viewer, whatever its role, so it makes no edit from then on, its large-file download included;
     - of the edits it held unsent, a transaction is applied only when every operation in it is safe: none touches an instance, a layer inside one, a main, a component set, an override record or a node holding a property's fields; none sets a field that links a node; none deletes or moves a subtree holding such a node; and no create puts back a node the file had, recognised by its id in the room's log of its last 10,000 revisions (not a permanent record: past that, a create putting back an instance, a main, a record or a node holding a property's field is still refused for what it is, and a plain layer put back can lose only property references left on it outside any instance or main, where they drive nothing). Anything else is refused whole, never in part, with a message its tab shows as it is: the change wasn't saved, and is to be made again after reloading;
     - it's sent nothing it can't read: the file, the log it catches up on, the transactions it hears and a refusal's nodes leave those properties and every keyed set out. It may show a property's old value until it reloads;
     - it reloads by itself: it asks for the build on reconnecting, and its update banner reloads once nothing is waiting to be saved (#167), each of its edits applied or refused by then. It isn't closed to reload, which would lose what it holds unsent;
     - a socket that hibernated on code from before this change keeps its attachment when the room takes this code up, without saying hello again. Every socket's attachment now records the protocol its hello said, and one that records none is treated as a tab from before records, under the same rule; a role change sent to such a tab keeps it a viewer (review 6, finding 5). The rule compares with the first protocol that knows records (`RECORDS_PROTOCOL`), so a later protocol bump keeps it.
     A version 1 client in a materialized file is told to reload, as before; one in a compact file views it, sent the file whole, never operations.
   - **Branches: a record's presence is part of it.** A record that exists differs from none: a side making or removing one changes it whole, conflicting where the other side did otherwise (both made one with other values); records on both sides are compared entry by entry (`changedFields`, in the editor's review and the room's SQL merge alike). The room migrates both sides of a merge, base included, so a base from before records compares records, not layers' values (review 6, finding 2).
   - **Branches: a record both sides made.** An override record main and a branch both made since the base (its id derives from its instance and path, so both name it alike) is compared field by field from an empty base, an unset field as `null` (`addedChanges`): a field both made alike isn't a change, one main left alone comes in, and one main made otherwise conflicts, to be resolved as any field; the fields taken come in as one create merged into main's record (`recordOp`), in the editor's review and the room's SQL merge alike. A record key both sides set first, differently, conflicts as any keyed value does (review 4, P2 #6).
   - **Copies' records made at once.** An override record is a copy layer's values (decision 0029), its id derived from its instance and path, alike on every client. Two clients writing the first value of one copy layer at once (a text's laid out size, after each set its text property) both make it; the room used to refuse the second whole transaction. Making an override record that exists now merges into it field by field (`mergeRecordProps`): `unset` is both lists, less the fields the create gives a value; a field the create sets or unsets is the later writer's; a field it doesn't mention keeps what the record has; `overrides` is both lists. Undone value by value, applied alike in the room, on clients, in stored replay and in a branch merge, so both edits stay, two people's explicit clears included (review 4, P1 #1).
16. **Compact copies and the room's memory.** No new node type. `propValues` is stored only on instances that aren't copies, a value at a time (item 15), bounded by its schema (item 3: 512 keys, 400,000 characters in all) and counted as any value is (decisions 0026 and 0029). `CopyView` presents driven fields from it (item 3), keeping per built instance a list of each copy layer's driven fields and keys, charged to its budget with the instance's copy layers (`refsBytes`) and given back when the instance is let go of, so the room's lazy reader, an instance at a time, holds it only for the instance it's at. An instance that set a property stores a value a layout reads, so a change to its main lays it out again (its texts may be another length). A `componentProps` value is bounded too (64 entries; names, descriptions, defaults and preferred lists capped). Both hold component ids (a swap's default, preferred values and an instance's chosen component), and a record's keys hold the ids of the main layers their scopes name, so they're listed in `heldNodeIds`: conversion, branch review and libraries see them.
17. **Libraries.** A published component carries its definitions; a swap's default and preferred values, an instance's chosen component in `propValues`, and the main layers a key's scope names, all in the library, are named as the library's copies are, and a component a swap only prefers is copied with it. Components whose instances no longer hold `variantProps` show as changed once, at the first publish after this change.
18. **Agent tools** (decision 0021): `set_props` writes an instance's `propValues` as the panel does, a value at a time into the record it's kept in (a nested instance's, its outer instance's), a value it no longer lists going back to its main's; a driven field set by `set_props` on a copy layer is the property's edit (item 3). The layers show it as soon as it's written, in both forms (review 3, P2 #7). Phase 4 adds `get_component_properties` and `set_instance_properties` (by property name, nested exposed ones by path), which make the same operations as the panel.

## Consequences

- Instances show Figma's properties and edit them, and the overrides list shows what a person changed.
- An instance's property values outlive changes to its layers (variants, renamed layers, layers added), as Figma's do. A set property costs a small record on the instance besides the layer overrides that show it.
- An operation can set one value of a map (`key`). Only `propValues` is written that way; the room, sync, branches and compact copies handle it, and every other property is set as before. Tabs before it view the file until their update banner reloads them, sent what they can read; of what they held unsent only safe transactions apply, and the rest are refused, saying to make them again (protocol 3).
- A driven layer's value is worked out where it's read, from the record and the main. Nothing writes values into layers after a teammate's edit, so no client sends anything it didn't do.
- In materialized copies, a layer synced from a file without a teammate's concurrent value shows its main's until the instance syncs again; the record has the value meanwhile. Compact copies have no such window.
- Editing a driven field by hand sets the property, so a text property's layers all change when one is typed in. A person who wants one of them different unlinks it from the property, and it keeps what it shows.
- An override is defined by layout, not by comparison: a value layout would give a copy isn't one, whatever produced it.
- A copy laid out differently from its main doesn't take its main's values for what layout decides when the main changes; layout gives them again. That's what layout-decided values already did inside auto layout.
- Until decision 0034, copies in a frame of another variable mode list their mode's fills and strokes as overrides.
- Instances of variants hold no `variantProps`, nor an override or an `unset` for it (the kit's 18,890 marks). The number of override records doesn't change: those instances have other differences too.

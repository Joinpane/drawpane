# 0035. Component properties and overrides, as Figma has them

- Status: proposed
- Date: 2026-11-17 (amended after six rounds of review, which kept values in a record on the instance; amended a seventh time on 2026-11-19 after the seventh review: values are a view over the layers they drive, kept as ordinary overrides, and the record, its migration and protocol 3 are gone, items 3, 8 and 14 to 18)
- Deciders: Ziyang (lead maintainer)

## Context

A 500k-layer commercial UI kit imported from a `.fig` (decision 0030) shows how far instances are from Figma's.

- **Properties.** Figma's Button has seven: Variant, State and Size (variants), Show Left Icon, Show Right Icon and Show KbdGroup (booleans) and Button Text (text). Drawpane shows the three variants only. Figma's Field has Orientation, Data Invalid and Description Placement (variants), Label, Description and Link (booleans), Label Text and Description Text (texts), Input Type (an instance swap), and, under a "Textarea" heading, the State and Placeholder Text of the nested Textarea instance, which Field exposes. Drawpane has variants and nothing else: no booleans, texts or swaps, no exposed nested instances. The importer drops `componentPropertyDefinitions` and notes "component-properties".
- **Overrides.** Drawpane lists every overridden property by its internal name. The Button lists nine: `Instance · radius, effects, height, minHeight, variantProps, width` and `Button · position, width, text`. Figma counts one change there: the text. The Field lists more than twenty (`Textarea · alignItems, gap, height, instanceOf, layoutMode …`).

Where the noise comes from, measured on the kit (503,466 nodes, 20,513 instances; the converter's output before `pinInstances`, then after):

| Marked overridden | Converted | Pinned | Why |
| --- | --- | --- | --- |
| `variantProps` on instances | 0 | 14,506 roots, 4,384 nested | Sync copies a variant's `variantProps` onto its instances, so `pinInstances` pins the instances that don't have it. It describes the main, like `componentDescription`, and no instance should hold it. |
| `width`, `height` on roots | 13,939, 9,037 | 11,887, 7,648 | The converter compares a root's size with its main's. Most of these roots hug or fill (`inst=hug main=hug`, `inst=fill main=fixed`), so layout decides their size. |
| `sizingH`, `sizingV` on roots | 7,411, 1,351 | 6,558, 677 | Fill is how an instance sits in its parent (Figma's `layoutGrow`, `layoutAlign`), so it belongs to the instance like its position. |
| `x`, `y`, `width`, `height` inside copies | 26,236, 18,873, 51,689, 29,409 | 24,646, 16,943, 52,619, 32,448 | Layers placed by auto layout, sized by hug or fill, auto-sized text, and children moved or stretched by their constraints in a frame the copy resized. Figma saves these laid out (`derivedSymbolData`, #171) and doesn't count them as overrides. |

Sync (`syncInstanceOps`) already leaves some layout-decided values alone, but only a nested layer's position and size in auto layout, hug sizes and auto-sized text, decided from the main's values. The converter's `markOverrides` checks none of it. `pinInstances` pins whatever sync would still change, so anything sync misses becomes an override.

What's left after that is real in Drawpane's model: a resized instance, a changed fill, a swapped icon. One kind isn't real in Figma: copies in a frame set to another variable mode differ in fills and strokes because the import stores each layer's resolved value. Decision 0034 makes those bindings resolved in the view, so the differences go away there, not here.

## Decision

### Properties

1. **Definitions.** A main component, or a component set for its variants, defines its properties in `componentProps`: an ordered list, at most 64, each with
   - `id`: stable, so renaming keeps every reference;
   - `name` (at most 64 characters), `description` (at most 500);
   - `type`: `variant`, `boolean`, `text`, `instance` (instance swap) or `slot`;
   - `default`: a boolean, a text (at most 10,000 characters) or a component id;
   - `preferred`, for an instance swap: component or set ids, at most 64, in order.

   A variant's values stay in its variants' `variantProps` (they decide which variant an instance is). Its entry in `componentProps` gives it its place in the order and its description. A set without entries for its variants shows them first, as now.
2. **References.** A layer says which of its values a property drives in `propRefs`: `{ visible?, characters?, instanceOf?, slot? }`, each a property id. A boolean drives `visible`, a text `characters`, an instance swap a nested instance's `instanceOf`, a slot a frame's content (decision 0032). One property may drive several layers.
3. **Values are the values of the layers they drive.** An instance's value for a property is the value of the layers in its copy that reference it (`propRefs`): `characters` for a text, `visible` for a boolean, the nested instance's component for an instance swap. A reference belongs to the component whose main it was set in: a copy layer that doesn't hold its own references (`propRefs` not among its overrides) takes its main layer's, so it's followed down its copy chain to the layer that does, and the main around that layer owns it (`referenceOwner`). Property ids are unique only within one component's definitions (a library's component and a local one can share one), so every lookup is by owner and id: an outer property drives only the layers whose references were set in that exact main, at any depth, a layer inside a nested instance that the outer main bound to it included, and a nested component's own properties are reached only through that nested instance (review 8 of #187, B5). Being in the same component set doesn't make a nested main's references the outer one's: a nested instance of another variant is another occurrence of the property, a definition the set shares included. Which definitions exist is the set's and the main's; ownership only says where they apply (review 9, R9-B1). Nothing else holds a value, so nothing has to agree with anything: the value follows main's override rules, in both copy forms, and every path that already handles overrides (sync, variant switch, swap, detach, conversion, branches, paste, libraries, agents, older tabs) handles values with no new code.

   - **Editing.** Setting a property writes the field on every layer it drives, as ordinary overrides, in one transaction. An instance swap swaps every nested instance it drives in one transaction, then syncs them, in the same undo step, as any swap does.
   - **Resetting.** Resetting a property clears those layers' overrides for the field it drives, and they take their main layer's value again, with what it depends on. Any override's reset does that now (`resetDependentOps`): the variable bound to the field comes back, and the text style once no other typography stays changed; a reset swap rebuilds the nested instance's layers from the component it goes back to. Resetting one variant axis puts that axis back and keeps the others: the instance switches to the variant that has them, and stays changed while any axis differs.
   - **"Mixed".** Layers can disagree: one edited by hand, or added to the main after the instance set the value. The panel then shows the property as "Mixed" (an empty text with "Mixed" as its placeholder, a switch labelled "Mixed", a swap picker reading "Mixed"), with its reset, and an edit sets them all.
   - **Variant switches.** A switch carries overrides by layer name, as a swap always has. Then each property the instance changed, and whose layers agreed, takes the same value, by property id, on the new variant's layers that the name carry gave nothing for that field, in the same undo step: a label named differently in the other variant keeps its text, as in Figma, and a field the name carry kept (another layer's text, edited on its own, that has the same name there) is never replaced (review 8 of #187, B2). A value whose layer the new variant doesn't have is dropped, as main drops any override on a layer the other variant lacks, and undo brings it back.
   - **Swapped nested instances.** A nested instance swapped for another component takes that component's values, except where it sits (its root-local values) and the fields the outer component's properties drive (`boundaryDrivenProps`): those stay its main layer's. Swapping the icon doesn't show an icon a boolean hides.
   - **Concurrency.** Two people's edits of different properties are edits of different fields, and both stay; of the same property, the later write wins, as for any field. An edit and a reset of the same property behave as an edit and a reset of any override.

   *Why not a record on the instance.* Six amendments kept values in a record on the instance (`propValues`), so that a value would outlive its layers: a round trip through a variant without the label, a layer added to the main after the value was set. Each round of review found data-loss schedules in what that took: a second store of the value to keep in step with the layers, then one store and every reader presenting it, a migration for files from before, a protocol for tabs from before, record-aware merges and handoffs at every boundary. The seventh review found five more, four of them at boundaries the record had added (an agent's commit around the migration, a fold skipping targets, a branch fold reading a reorder as edits, a stale detach making an instance without a record). The fifth, a nested instance losing its component link when a detach crosses a delayed swap, is on main too, and is fixed on its own (#209). The record's gains over the view are those two cases, where the view does what main does for any override, so the record is gone, and with it the migration, protocol 3, the old-tab rules and every handoff.

4. **Defaults.** A main's layers hold its defaults: a boolean's layers are visible when its default is true. Changing a default on the main sets those layers, so instances that haven't changed it follow, as any main edit reaches them.
5. **Nested instances.** A nested instance in a main can expose its properties (`exposeProps`, Figma's `isExposedInstance`). An instance shows them under the nested instance's name, below its own, and through exposed instances inside it in turn. A nested instance that isn't exposed keeps its properties to itself, as in Figma.
6. **Renaming, reordering, removing.** Rename and reorder edit `componentProps`. References name ids, so they stay intact. Removing a property removes its references in the main, and its layers keep their current values.

### Overrides

7. **What an override is.** An override is a value a copy holds that layout wouldn't give it. Laid out means one of these:
   - for an instance root: its position, and on an axis where it or its main fills, its sizing and size;
   - a layer placed by its parent's auto layout: its position, and its size on an axis that hugs or fills;
   - a layer that hugs: its size on that axis;
   - auto-sized text: its width when it grows sideways, and its height unless its size is fixed;
   - a child of a frame without auto layout whose size differs from its main's: its position on an axis pinned to the end or centre, and its position and size on one that stretches or scales, each only while it's what the constraint derives from its main layer's (`constrainedValues`, within 0.01). A child moved or resized on top of that holds a person's change, which is an override (review 8 of #187, B1).

   One function (`laidOutProps` in `@drawpane/model`) decides it for the converter's `markOverrides` and for `pinInstances`: an import doesn't mark them. Sync and resets don't just leave them alone: a value layout derives from the main's is derived again. A child pinned to the end, centre, both edges or scaled, in a copy frame of another size, takes its main layer's place moved by the constraint (`constrainedValues`), when its main layer moves and when its override is reset. Values auto layout, hug and auto-sized text decide are left to the layout pass, which gives them again. Laid out values are stored as decision 0029 says ("laid out", not overridden).
8. **Link properties.** `variantProps` and `componentProps` describe a main: copies don't take them from their main's layers, in either form, like `componentDescription`. `propRefs` and `exposeProps` are copied like any value, except on an instance root, where they're how it's used in the main around it (`ROOT_LOCAL_PROPS`).
9. **The overrides list** shows what changed, in words, grouped by layer, nested instances under their path ("Textarea › Placeholder"):
   - names a person uses: "Text", "Fill", "Stroke", "Hidden" or "Shown", "Size", "Position", "Corner radius", "Effects", "Swapped to Check";
   - values a property shows above aren't listed again: a property row shows its own changed mark and reset (a driven layer edited by hand makes its property "Mixed", item 3);
   - a reset per item, which resets that value on that layer only. Today's reset syncs the whole instance, which would also undo every laid out value in it;
   - "Reset all", which resets the instance's changes, those inside its nested instances included, as Figma's does.

### The instance panel

10. Like Figma's, one row per property in the definitions' order: a dropdown for a variant (a segmented control for up to three values; a switch when its values are true and false), a switch for a boolean, a text field for a text, a picker for an instance swap (its preferred values first, then the components it can swap to). A row that differs from its main has the component dot beside its label and a reset. Exposed nested instances follow, each under its name as a heading. Then the overrides list, then Swap and Detach.
11. **On a main or set:** the definitions, each with its type, default and description. They can be renamed (double-click), reordered (drag) and removed; "Add property" offers the types and, for a boolean, text or swap, links the selected layer. A layer in a main shows which property drives it, with a way to unlink it.

### Import

12. **REST** (`GET /v1/files/:key`): a component or set's `componentPropertyDefinitions` (keys are `name#id`, variants just `name`; `type`, `defaultValue`, `variantOptions`, `preferredValues` by component key); a layer's `componentPropertyReferences` (`visible`, `characters`, `mainComponent`); an instance's `isExposedInstance`. Keys map to ids of their own, the same every time the same file is imported. Preferred values name components by key, matched to the file's components, or dropped when they're in a library the import doesn't bring.
13. **`.fig`**: Open Pencil's scene graph has the same (`componentPropertyDefinitions`, `componentPropertyReferences`, `isExposedInstance`). `@drawpane/fig`'s adapter writes them in the REST shape, so one converter reads both.
14. **Instances' values** come in as overrides on the layers they drive, where they differ from the main layer's by more than layout (item 7), as any value does. A copy's layer that leaves `componentPropertyReferences` out takes its main layer's; one that lists them, an empty list included, keeps its own (`propRefs: {}` when empty), marked as an override like any difference, in both copy forms. So a layer Figma has unlinked keeps its text when a property is set later. The REST case is covered by a constructed fixture; the `.fig` scene graph can't tell an empty list from none, so a `.fig` copy takes its main layer's references.

### Everything else

15. **Sync and undo.** Definitions, references and values are properties set by operations, so collaboration, undo, branches and merges treat them as any value. There's no new operation, no protocol change, and nothing a tab from before this change can't read: it shows the values on the layers, and an edit it makes of a driven layer is the property's value, everywhere. What's left is what main has for any override:
   - an edit and a reset of the same field made without seeing each other: a layer already marked sends no marks with the edit, so a reset reaching the room first leaves the edit's value unmarked, and a later sync of a materialized copy gives the main's back (a follow-up for overrides in general);
   - with compact copies, an edit of a copy layer made without seeing a teammate's detach is refused: its override record would be made where the plain layer now is, or, after a variant switch too, under what's now a plain frame. Both reproduce on main without properties (a follow-up too).
16. **Compact copies and the room's memory.** No new node type and nothing new stored on instances. `componentProps`, `propRefs` and `exposeProps` are bounded by their schemas (64 definitions; names, descriptions, defaults and preferred lists capped) and counted as any value is (decisions 0026 and 0029). A swap definition's default and preferred components are listed in `heldNodeIds`, so conversion, branch review and libraries see them.
17. **Libraries.** A published component carries its definitions; a swap's default and preferred components in the library are named as the library's copies are, and a component a swap only prefers is copied with it. Components whose instances no longer hold `variantProps` show as changed once, at the first publish after this change.
18. **Agent tools** (decision 0021): `set_props` sets a driven field as any field, which is the property's value. Phase 4 adds `get_component_properties` and `set_instance_properties` (by property name, nested exposed ones by path), which make the same operations as the panel.

## Phases

1. **Import and edit on instances.** Model `componentProps` (boolean, text, instance swap; variant order), `propRefs` and `exposeProps`; import them from REST and `.fig`; the instance panel shows and edits them, nested exposed ones included; the overrides list in words, per-item reset of one value, reset all including nested instances; the noise gone from imports (items 7 and 8). Tests without the kit, an end-to-end test that toggles a boolean and edits a text on an imported instance, and the kit measured with `tools/kit-parity`.
2. **Authoring on mains.** Creating, renaming, reordering and removing properties; defaults and descriptions; linking layers; the main's panel.
3. **Slots** (decision 0032) as a property type.
4. **Libraries and agent tools.**

## How it's verified

- Each laid out case of item 7 has a test where a copy's value differs from its main's: the import doesn't mark it, sync doesn't change it, and changing it by hand marks it. A constraint-placed child also gets its derived place back when its main layer moves and when its override is reset.
- Item 3, in both copy forms (`component-property-values.test.ts`, the first review's cases): a value carried across a switch to a variant whose layer has another name; one dropped at a variant without its layer, undo bringing it back; "Mixed" when a layer the main adds or a hand edit disagrees, an edit setting them all and a reset clearing them all; a swap leaves a boolean's value; a reset brings back the variable binding; resetting a swap rebuilds its layers, for undo and other clients; resetting one variant axis keeps the others; a library insert names a swap's components as its copies.
- Under collaboration, in both copy forms, through a room stand-in and real sync replay (`component-property-view.test.ts`): an edit is one transaction writing every driven layer; an edit and a reset at once, of the same property (the later one's value, everywhere) and of different ones (both stay); a variant switch carrying values by id, and its undo; a detach keeping what the layers show; a branch merge of different properties, and a conflict on the same one; a tab from before properties editing a driven layer by hand, offline, its edit the property's value. The override-mark race of item 15 is a pinned follow-up test.
- A property test (`component-property-convergence.test.ts`): three clients make random edits, resets, variant switches, swaps, nested values, layers added to mains, detaches and undos, sending and receiving in random order, their sockets dropping and coming back, one of them in a variant a tab from before properties editing layers by hand, in another three levels deep with a nested copy swapped by hand. Once everything is delivered every client and the room hold the same file, every row says what its layers hold (their value, or "Mixed"), and an edit of each property then sets every layer it drives, on every client and in the room's file.
- The eighth review's cases: a constrained child of a resized copy, for each constraint, place and size, as derived or changed on top, through the REST importer and `pinInstances` (`constrained-overrides.test.ts`); a nested component's property, and a library component's, sharing the outer one's id, and a layer inside a nested instance the outer main bound to its own property; a variant switch where a field the name carry kept is left as it is; a nested instance of another main in the same set, with per-main and set-level definitions (`property-scope.test.ts`). Each in both copy forms where copies are involved.
- The compact equivalence suites (decision 0029) run as before.
- The kit: overrides counted before and after, the panel's property count against Figma's for the Button and two other components, and every sampled frame drawn against main's.

## Consequences

- Instances show Figma's properties and edit them, and the overrides list shows what a person changed.
- A value is its layers' value, an ordinary override: everything that handles overrides handles it, and nothing else stores it. A value whose layer a variant doesn't have is dropped at a switch to it, as main drops any override there, and a layer the main adds later shows its main layer's value, the property "Mixed" until it's set again.
- An override is defined by layout, not by comparison: a value layout would give a copy isn't one, whatever produced it.
- A copy laid out differently from its main doesn't take its main's values for what layout decides when the main changes; layout gives them again. That's what layout-decided values already did inside auto layout.
- Until decision 0034, copies in a frame of another variable mode list their mode's fills and strokes as overrides.
- Instances of variants hold no `variantProps`, nor an override or an `unset` for it (the kit's 18,890 marks). The number of override records doesn't change: those instances have other differences too.
- Measured with phase 1 on the kit: override marks fall from 294,708 to 160,968, instances with any from 17,825 to 9,282, and what's drawn doesn't change.
- Measured with values as views (the seventh amendment), at ba63ec0 against main at af07ef0, both converted fresh: override marks 295,576 to 161,797, instances with any 17,825 to 9,282, and what's drawn doesn't change (761 frames: median 0.78, p90 3.27, total 1,183.33 on both; none better, worse or changed). The panel shows Figma's definitions: the Button's 7 on its 1,542 instances of a default-size variant (its 809 icon-size ones show their 3 variants: no layer in those variants takes the text or the booleans), the Badge's 6 on all 312, the Checkbox's 8 on all 502, the Field's 10 on 600 of 606 (with its exposed InputGroup's 7 under it).
- Measured again after the eighth review's fixes, at bb23070 against main at af07ef0: override marks 295,576 to 162,812 (1,015 more than at ba63ec0: 512 `x`, 303 `y`, 92 `width`, 108 `height`, constrained children holding something other than what their constraints derive, now kept). 371 of those are within a pixel of the derived value (Figma 212 where the constraint gives 211.571), which looks like Figma rounding a constrained layout to the pixel grid; they're kept by the 0.01 rule, as overrides of what's drawn anyway. Instances with any override stay 9,282, nothing drawn changes (761 frames), and the panel counts are the same, nested instances' included (the Field's Textarea shows its 2).

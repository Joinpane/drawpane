# 0029. Copies stored as their main plus what's overridden

- Status: accepted (phase 4 of decision 0027). Phase 4a (the model, the editor's view, the equivalence suite) and 4b (the room stores the compact form, sync, converting stored files) are built.
- Date: 2026-11-16
- Deciders: Ziyang (lead maintainer)

## Context

An instance is a frame (`instanceOf`) whose every layer is a stored node, `mirrors`-linked to its main's layer, and an edit to a main is written into every copy in the same transaction (decision 0010, `components.ts`: `propagationOps`, `syncInstanceOps`). That kept the renderer, layout and hit testing free of special cases, and made every client agree, because copies are just nodes. At the size of real kits it's what costs most (decision 0027):

- **Size.** The shadcn/ui Pro kit saves 101,000 layers in Figma and 503,000 in Drawpane: a copy is stored, synced, kept in undo and snapshotted layer by layer.
- **Editing a main** writes into all its copies: 7 s for a main with 13,174 copies at 500,000 layers, and a transaction the size of the copies.
- **Loading part of a file** (phase 3) is impossible: a client with one page loaded can't write a main edit into copies on pages it hasn't loaded.

What sync already does narrows the change. A copy's properties equal its main's except two kinds (`syncInstanceOps`): those marked overridden (`overrides`), and those layout decides for the copy (position in auto layout, hug and fill sizes, auto-sized text). Its structure always equals its main's: sync deletes layers the main doesn't have and recreates missing ones, and imports detach copies whose structure differs (`pinInstances`). So a copy holds nothing of its own except where it differs.

## Decision

**Store what differs; present everything.** The document stores instance roots and, for a copy layer that differs from its main's, an override record. The editor's `Doc` presents every copy layer as an ordinary node, built from its main and its override record, so the renderer, layout, hit testing, the layers panel, the inspector, export and the agent tools read copies exactly as now.

1. **Stored form.**
   - An instance root stays a stored frame with `instanceOf`, its root-local properties (position, constraints) and its own overrides, as now.
   - The layers inside a copy aren't stored. One that differs from its main's is stored as an **override record**: a node of a new type, `override`, under the instance's stored root, holding the `path` of main layer ids from the root's main down to the layer (through nested instances, whose own mains continue the path), the properties that differ and the `overrides` list.
   - Nested instances inside a main are part of the main and stored as now; nested instances inside a copy are copies like any other layer. Swapping one is an `instanceOf` override on its record, and its layers follow the swapped-in main from there.
2. **Ids.** A copy layer's id is derived: a stable hash of its instance root's id and its path, 16 base-62 characters (like library copies in decision 0010, so it fits the 64-character id rule however deep the nesting). Its override record has that same id. Every client, the server and any tool derive the same ids, so selections, comments, prototype links and operations can name a copy layer that isn't stored.
3. **The editor's view (`Doc`).**
   - `get`, `childIds`, `nodes`, `ancestors` and `pageOf` return copy layers built on demand and cached: the main layer's properties (itself possibly built, for mains containing copies), minus the link properties, plus `mirrors` (the main layer's id, as now), plus the record's properties. Parent and key come from the main's structure. Code that reads `mirrors`, `instanceOf` and `overrides` keeps working.
   - `apply` takes operations as now. A `set` on a copy layer becomes a `set` on its override record, created when it's the first. Creating, deleting or moving layers inside a copy is refused, as sync would have undone it. `apply` returns the operations as stored; those are what undo and sync record.
   - When a main or anything it uses changes, the copies built from it are dropped from the cache and rebuilt when next read. Change notifications name the copy layers affected, so the scene's cached matrices and bounds and the renderer's index (decision 0028) follow.
4. **Layout.** A copy's layout-decided properties equal its main's while nothing about its layout differs. When something does (the instance resized, a text overridden, a layer hidden), the editor lays the instance out as now and stores the values that differ in the override records, marked as laid out rather than overridden. When a main changes, the editing client lays out again only the instances of it whose layout differs (an index kept by `Doc`), and stores what changed. Every other copy follows its main with no operation at all. Layout stays computed once, by the client that made the change, and stored, so clients never disagree over text measurement.
5. **Editing a main** is the main's own operations, plus the relayout of the instances whose layout differs. `propagationOps` goes.
6. **The server** stores and validates what it's sent. An override record must sit under an instance root, its path must be well formed and its properties must pass their schemas; whether a property applies to the layer's type is checked where copies are built. Paths that read layers (MCP, thumbnails, export, search, library manifests) build copies with the same function the editor uses, moved to `@drawpane/model` so it runs anywhere, an instance at a time.
7. **Detaching** builds the instance's layers as real nodes, in one transaction, and deletes its override records, as an edit would. (Phase 4a keeps their ids: see below.)
8. **Imports** (Figma, `.fig`, Penpot, the kit store) write the stored form directly. `pinInstances` turns what a copy keeps as made into override records instead of `overrides` on full nodes.
9. **Existing files** are converted when their room next loads (a format version in the room's meta). A version named "Before compact copies" is saved first. Copy layers that equal what they'd be built as are dropped; the rest become override records with derived ids. References to old copy ids are rewritten from the conversion's map: comment pins (D1 `comments.node_id`), prototype links, reading orders and agent sessions. Older version snapshots and branch bases are converted when read, so restoring and merging keep working. Clients learn the format at hello, and an old client reloads.

## Phase 4a: what was decided where this left room

Built in `@drawpane/model` (`copies.ts`) and the editor (`compact-copies.ts`, `Doc`), proven against today's model, and not yet stored or synced.

- **Hash.** `copyId(root, path)` is chained SHA-256 (FIPS 180-4, carried in the model as `sha256` because Web Crypto's digest is asynchronous): from the instance root's id, each step is `base62(sha256(parentId + "/" + element))`, 16 characters taken from the digest's bytes under 248 (`byte % 62`, without bias), about 95 bits. Each step is a single SHA-256 block, about 1.5 µs. `copyChildId(parent, element)` is one step. A collision with a built copy or a stored layer is refused when the copy is built.
- **Paths.** An element is the id of the main's layer as the main presents it: the copy's `mirrors`. So a copy layer's id is `copyChildId(its parent's id, its mirrors)`, and through a nested instance the path goes on with that instance's copy ids in the main (or a swapped-in main's layer ids). Stored ids would have been shorter to explain, but a copy's id would change whenever what it copies becomes stored: detaching a nested instance inside a main, or deleting a main whose instances keep their layers. With presented ids those keep the same ids, and so do every override record and selection that names them.
- **Stored form.**
  - A record sits under its instance's stored root with one order key (`OVERRIDE_KEY`), since records aren't layers.
  - `applyOp` refuses three things: a record whose id isn't the one its path derives, a record that is moved, and clearing `instanceOf` on a root that still has records.
  - A record holds every value that differs exactly from its main's (an explicit default included, because the editor compares values). It also holds every overridden value, so the copy stays put when the main changes, and `unset`, the properties it lacks where its main's layer has them (a stored value can't be null).
  - An instance root stores its root-local properties (`x`, `y`, `rotation`, flips, `lockAspect`, `positioning`, constraints, `instanceOf`) and whatever else differs, by the same rule.
- **Laid out vs overridden.** No marker is needed: a value in a record whose property isn't in its `overrides` is laid out. Layout and other derived writes go through the same translation, so a laid-out value equal to the main's is dropped, and the copy follows its main again.
- **Swapped nested instances.** A record's `instanceOf` swaps its copy. The copy is then that main's instance, placed where its source is: root-local values from the source, the rest from the swapped-in main, as an instance root has them. Its layers are the swapped-in main's.
- **The flag.** `new Doc({ compactCopies: true })`, or `setCompactCopiesDefault(true)` for every new document. The web app turns it on from `localStorage` `drawpane:compact-copies`, as a developer switch until the room stores the form. With the flag on:
  - `Doc.reset` converts the materialized snapshot it gets (`resetIds` says how copies were renamed), and `resetStored` takes the stored form as it is.
  - `apply` takes operations on presented layers and returns their inverse in the same terms, so the history and undo need nothing new. The stored operations it made are `lastStoredOps`, which is what phase 4b sends to the room.
  - `applyStored` applies stored operations as they are.
- **Operations on copies.**
  - A `set` rewrites the record so it holds exactly what then differs.
  - Creating a layer inside an instance is accepted only when it matches a copy the instance presents (same `mirrors` and type). It's absorbed into that copy's record, which is how materialized copies come in: `instantiateOps` from an older client, a paste, a library insert.
  - Deleting or moving a copy layer is refused.
  - Unlinking a root (detach, a deleted main, a main that stops being one) makes its copies stored layers with the same ids. Relinking it absorbs them back into records, which is how undo restores both.
- **Editing a main.** `propagationOps` writes nothing with the flag on. Relayout covers only two kinds of instance:
  - an instance whose layout differs from its main's (an index kept by `Doc`: it stores a value a layout reads), when its main's layout inside may have changed;
  - an instance whose main changed size, so its parent lays it out again.
  A main holding instances of a resized main counts as changed inside, however deep. Changes no layout reads (fills, names, a child of a frame without auto layout) lay out nothing.
- **Fixed in today's model too.** The equivalence tests found these:
  - Swapping a nested instance now marks `instanceOf` overridden, and its outer instance's sync keeps the swap and follows the swapped-in main. Before, the next sync reverted it, or kept the old main's name and size.
  - Reset and swap sync a nested instance through its outermost instance. Syncing it against its own main had rebuilt its layers off the chain of copies.
  - An edit to a main reaches the copies swapped to it.

### Verified

- **Equivalence on corpora** (`packages/corpus/test/compact.test.ts`): converting, then building every copy, gives the file back with ids mapped, exactly. The stored form passes the room's checks, and it is canonical (building and converting again gives it back). This holds for:
  - generated kits of 3,000 (two seeds), 20,000 and 60,000 layers;
  - the `.fig` samples (pattern, tailwind-ecklf, medianova), converted and pinned as imports are;
  - the Penpot fixtures (file-with-library, svg-attrs-camel-case, showcase).

  A 60,000-layer kit stores 6,548 nodes instead of 60,275 (19.4 MB of JSON to 1.2 MB).
- **The same kit both ways:** a kit generated through the compact view is the same tree as the one generated today, at 3,000 and 20,000 layers.
- **Edits** (`packages/editor/test/compact-equivalence.test.ts`): random sequences, applied to a document as today and to the same document converted, give the same document after every step, compared layer by layer. The edits are fills, opacity, hiding, texts, font sizes, gaps, widths, swaps (top-level and nested), resets, detaches, new instances, adding and deleting layers in mains, undo and redo. Five runs of 400 sequences each, with random seeds, were clean. They differ, on purpose, in two places:
  - after a swap between mains laid out differently, today's model first lays the new layers out by the old main's settings;
  - a hidden layer in an auto layout keeps where it last was in today's model, and takes its main's place in a compact copy (neither is drawn).
- **The editor suite** runs a second time with the flag on (`pnpm test`), the monkey fuzzer included, as does `pnpm fuzz`. The editor's view has its own tests: edit a copy's text, edit a main and read a copy, swap a nested instance, reset, detach, delete a main, undo and redo.
- **Measured** (the scale benchmark of decision 0027, `BENCH_COMPACT=1` against off, on this VM, Chromium without a GPU, as the generated kit opens):

  | | 100,000 layers, off | on | 500,000 layers, off | on |
  | --- | --- | --- | --- | --- |
  | Stored | 100,182 nodes, 32 MB | 10,982 nodes, 2 MB | 500,038 nodes, 162 MB | 51,043 nodes, 8 MB |
  | Load (one document reset) | 148 ms | 1,584 ms | 833 ms | 5,870 ms |
  | First frame of the largest page | 1,000 ms | 1,166 ms | 1,041 ms | 1,227 ms |
  | JS heap for the file | 42 MB | 54 MB | 169 MB | 220 MB |
  | Edit the most used main: the commit | 1,292 ms | 9 ms | 6,820 ms | 30 ms |
  | Edit the most used main: drawn | 2,142 ms | 767 ms | 7,653 ms | 840 ms |

  The edit is a fill on a main with 2,607 copies (100,000) and 13,174 (500,000), as in decision 0027. Its commit no longer grows with the copies. What's left until it's drawn is the renderer repainting the whole page fitted to the window, the same in both models: phase 2's to bring under 100 ms. Panning and zooming are within this VM's noise of off.

  Loading is slower and holds more because, in 4a, the client converts the materialized snapshot it gets (about 1.5 s per 100,000 layers headless) and caches every copy it builds. Converting moves to the room in 4b, which sends the stored form; building copies a page at a time is phase 3's.

  Edits a layout reads cost what the layouts they change cost. Headless, at 500,000 layers, a main's text took 15,111 ms before and 6,312 ms now; its gap 14,741 and 6,211; a layer's width 22,775 and 14,114. A main that changes size moves its instances and what's beside them on every screen it's on, and those positions are stored outside the copies, so every such screen is laid out again (the time is the layout engine's). Changes no layout reads (a fill, a layer's opacity) take 16 ms and 13 ms.
- **Not verified yet:** the kit store's Penpot kits (`$PENPOT_KITS`, not in the repository) and the converted shadcn/ui pages; collaboration, which needs 4b.

## Phase 4b: what was decided where this left room

Built in the room (`apps/worker/src/rooms/convert.ts`, `presented.ts`, `file-room.ts`), the model (`convert.ts`, the snapshot header, the protocol) and the editor's sync; the developer switch is gone.

- **Format per file.** The room's meta says how the file stores copies: `copies` is `compact` or `materialized`. A new file starts compact. A room from before 4b has no `copies` and is materialized; it converts when it next loads (decision point 9). `COMPACT_COPIES=off` (an environment variable, as `UPDATE_CHECK` is) stops conversions and makes new files and imports start materialized; a room keeps serving whatever form it holds.
- **Converting a stored file.**
  - The room saves a version named "Before compact copies" first (streamed, as any version), then converts in steps run by its alarm; between steps it serves everyone as usual, and the file stays materialized and editable until the last step.
  - A step is bounded by the work it does, not the clock: on Cloudflare `Date.now()` doesn't move while code runs without I/O, so a step timed by it would convert the whole file. It reads and writes about `CONVERT_STEP_WORK` (60,000) rows and reads about `CONVERT_STEP_BYTES` (8 MB) of values, at least one instance, and stops before an instance that would take it past either.
  - An instance is held whole while it converts, and built from its mains, so its size is decided before any of it is read, in SQL (`PresentedCounter` in `rooms/convert.ts`): its layers (`COUNT`); the layers building it creates, as its main presents them (a nested instance counts its own main's layers again, however deep, and a copy swapped to another main counts that main's: an upper bound); the nodes building it reads, each once; and the bytes of their values (its own, its main's, the mains of instances among its layers, theirs, each with its layers: `SUM(LENGTH(CAST(props AS BLOB)))`, UTF-8 as stored). One of more than `MAX_INSTANCE_LAYERS` (5,000) layers, `MAX_INSTANCE_BUILT` (10,000) layers built, or `MAX_INSTANCE_BYTES` (8 MB) stops the conversion as a failing step does (below): the file stays materialized and working. The byte bound charges `LAYER_BYTES` (256) for every node read and every layer built on top of their values, since a layer of empty values costs two bytes stored and several hundred in the heap (the memory check measured about 700 near a 64 MB heap's limit). Counting stored layers alone wasn't enough: an instance of 4,000 texts of 20,000 characters ran a 128 MB heap out; and counting bytes alone wasn't either: an empty instance of a main of 200,000 empty rectangles did (100,000 a 64 MB heap), building every copy before it found the instance doesn't match. Out of memory, no catch runs to mark the conversion failed. UTF-8 bytes are what V8 holds for Latin-1 text, and as little as half of it for text V8 stores two bytes a character; the bound leaves room for that (below). Tables converted as they're read (an import, a version, a branch's base: `compactTable`) are converted in the same steps, under the same bounds, and one over them is refused with the same message.
  - **What a step holds is bounded as it's built, not counted beforehand.** The counts above missed a shape three times (the intermediate copies of nested mains a build makes and keeps on the way, their paths, mains that contain their own instances), so they're only a cheap first filter now. Everything that builds copies on the server charges a `BuildBudget` (`packages/model/src/budget.ts`) for what it makes and keeps, and gives it back when it lets go: every copy layer built (its slot, its path, its entries in the view's maps; intermediate copies of nested mains included), every presented node cached (with its values), every row the reader parses and keeps (`SqlConversion`'s caches, an instance's layers as they're read, a row at a time). Costs are estimates of V8's heap, measured in Node: about 800 bytes a slot for short paths and up to 19 more a path element for long ones (`slotBytes`: 600 plus 16 an element came out at 0.86 to 1.05 of the measured heap on chains and fans); values a byte a character, two past Latin-1, counted again wherever they're held (text-heavy instances come out at about 0.6, on the safe side). One budget covers a step, `BUILD_HELD_BYTES` (24 MB). Between instances, past half of it, the step lets go of what it cached. Past it, `BuildTooLarge` is thrown and everything built is let go of: if the step settled other instances first, it ends there and the next step tries that instance afresh; afresh, it can't be built within the budget, and the conversion stops (`InstanceTooLarge`), the file staying materialized and working. Because a step converts at least one instance or stops the conversion, it always moves on.
  - An instance at a time, in dependency order: the instances inside a main, and a main that is itself an instance, before the instances of that main (`InstanceConverter` in the model, the same steps `compact` takes in one pass). Only the instance and the mains it's built from are read.
  - Each instance is checked before it's kept: built from what was written, its copies must be its materialized layers exactly, ids renamed, drawn in the same order. Siblings draw in order of their keys, then their ids, wherever they're stored; built copies follow their main's order. So siblings sharing a key whose ids sort the other way round from their main's would draw differently built, and that instance isn't kept as converted. One that isn't is **detached**, explicitly: its root and every layer are kept as stored layers, unlinked from the main (no `instanceOf`, `mirrors` or `overrides`), so it looks exactly as it did and no longer follows its main. That's what 4a's `compact` and the importers' `pinInstances` already do. It's logged with the reason, kept in the room's `copies_log`, and listed by `copiesFormat()`. We chose detaching over keeping materialized instances supported: the editor's compact view would need a third kind of instance, and every path would have to handle it, for files that, on every corpus we have, convert without one.
  - What it decides is written beside the file, not into it, each instance in its own storage transaction: the old copy ids and their derived ids (`conv_map`), the rewritten roots, override records and detached layers (`conv_rows`), what's settled and why (`conv_done`), what each instance was built from (`conv_deps`). A conversion cut short (the room evicted, a deploy) resumes from there. Each step reads these tables afresh, as a restarted room would.
  - Edits made during the conversion go to the materialized file as ever. Each marks, in its own storage transaction, the instances it may have changed: an instance it's in, and every instance built from a main or set it's in. Their decisions are dropped and they're converted again. An instance deleted or unlinked before its turn is settled as gone (made again, by an undo say, its edit marks it again). Marking happens in SQL: the instances an edit marks (every instance of a main, in a kit) are gathered into a table of their own and their decisions deleted there, and so are those of instances no longer listed; nothing of them is read into memory.
  - Applying waits for a step that listed the file's top-level instances afresh (edits may have made or removed some) and found every one settled. In the storage transaction that applies, they're listed once more and it waits if any is new; and once applied, if any instance of a live main would still store layers, the transaction is rolled back and the conversion goes on (five times in a row, and it stops, as a failing step does). The decisions are applied in one storage transaction: copy layers deleted, rows written, ids held elsewhere renamed. Renaming reads only the rows that hold a non-empty reading order, reactions or flows (found in SQL), a row at a time, and only those values, writing back what changes in place (`renameHeldIdsIn`): a text's characters are never read. Nobody sees a half-converted file.
  - Applying is one revision, not logged as operations, like an import: clients behind it load the file rather than catch up. An agent session's undo doesn't reach back past it (its operations were in the old form).
  - A step that throws stops the conversion for good (`conv_failed`), and the file stays materialized and working; the error is logged.
- **Undoing it.** With `COMPACT_COPIES=off`, restoring "Before compact copies" (or any version saved before the conversion) puts the file back as it was stored then, materialized: the file is replaced whole, in one storage transaction, everyone loads it again, and the state before is saved as a restore point first, as any restore does. Comment pins on copies go back to their old ids, from the conversion's map (see comment pins below). With conversion on, restoring that version converts it as it's read, which undoes edits but keeps the compact form. Restored materialized, the file forgets that conversion's backup (`conv_backup`), so converting it again, once conversion is turned back on, saves a new "Before compact copies" first, holding the edits made since.
- **Ids other things hold.** Every id-valued property was checked (`heldNodeIds` lists the ids each holds; a test checks it against every property whose schema takes an id, the ids that aren't nodes' aside: a collection's modes, a library's file and publish): `readingOrder`, prototype `reactions` (`navigate`, `overlay`, `swap-overlay` destinations) and `flows` (`start`) can name a copy layer; `instanceOf`, `mirrors`, `textStyle`, `bindings`, `variableModes`, `values` aliases and library links name mains, styles, variables and collections, which keep their ids. The three are renamed with the conversion's map: inside an instance as it converts (so the check compares like with like), and in every node when the conversion is applied, override records and what the conversion wrote included, since an instance can name the copies of one converted after it (whose ids weren't known yet). Renaming twice changes nothing, so the check still holds. Agent sessions hold no node ids in D1; the room's call ledger stops at the conversion (above). An edit from a tab that loaded the file before it converted is checked for the ids it holds too: a layer named by its copy's old id in a reading order, a prototype link or a flow's start is renamed to the derived id from the conversion's map (`pin_map`); any other old copy id (a text style, a binding, a variable mode or alias) is refused, and so is a held id the file doesn't have and the map can't translate (after the week), with the reload message.
- **Comment pins** (D1 `comment_threads.node_id`). The applied conversion's map stays in the room for a week (`pin_map`, `rooms/pin-map.ts`), and a copy of it goes to R2 beside the file. While the room has it, a comment written or moved with an id of the form the file no longer has (a tab that hasn't reloaded) is translated as it's written: the Worker asks the room (`pinTarget`). The alarm moves every pin when the conversion is applied (then everyone is told to load the file again, their comments pinned), and once more before the room lets the map go. Restoring a version from before it with conversion off moves them back, from the map the room has or the copy in R2. After the week, a comment written or moved with an old id is translated through the copy of the map in R2 (read a line at a time). A comment is never pinned to a layer the file doesn't have: the room keeps an id it has (a stored layer, or a copy layer, looked for on the comment's page an instance at a time), translates one from the other form, and otherwise the comment is pinned to its point on the page, with no layer (a deleted layer, an id neither map names, or the map in R2 gone too). So is one whose id can't be translated because the map couldn't be read (R2 failing, a damaged copy that won't decompress) or the room couldn't be asked: the id as sent is never kept. Pins written with old ids before this shipped show at their saved place on the page.
  - Sweeps say which way they go and for which change of form: every change (a conversion applied, a materialized restore, an import in another form) counts a generation (`pins_gen`) in its storage transaction and asks for a sweep toward its form (`pins_sweep` = form and generation). A sweep checks, before each write to D1, that the file still has that form at that generation, and stops if not; it clears only the flag it was for. So a restore that lands while a sweep toward compact awaits D1 is followed by a sweep back, and the latest form wins. Each write moves a pin only from the id it read, so running a sweep again changes nothing more.
- **Protocol (version 2).** `hello` lists the forms the client reads (`copies`); `welcome` says the file's (`copies`); a version 1 hello is a client from before 4b, which reads materialized only. The room decides at welcome, after the hello's awaits, so a file that converted meanwhile is never sent to a client that can't read it.
  - **A tab from before 4b** (version 1) in a file stored compact is sent the file as presented (every copy built, an instance at a time, as the MCP tools read it, and the document's own nodes: text styles, variable collections and their variables, libraries) as a viewer, when it's small enough to send through a socket: at most 8 MB of JSON as presented (`SOCKET_MAX_CHARS`, the bound on what any client that can't download is sent), sent in chunks of at most 2,000 nodes and 1 MB. A socket has no backpressure, so what's sent is held until it leaves; such a tab can't download, and the room can't build a large file whole for it. A larger file is shown to it as one page saying "Drawpane was updated. Reload the page to see this file." (`reloadPlaceholder`, never stored). The size is measured before anything is sent: what's stored first, in SQL, then the presented file a node at a time, stopping as soon as it's past. We chose this over refusing old tabs every compact file: those tabs only live until their next reload (#167 offers it to tabs from after it, not to these), a small file stays readable, and no bound depends on the file's shape. The sixth review found the first version gathering 2,000 presented nodes with no bound on their bytes (a main of 400 texts of 200,000 CJK characters ran a 128 MB heap out before a chunk left) and leaving out the document's own nodes. Its edits are refused with "Drawpane was updated. Reload the page to edit this file.", which that client shows; it's sent the file again as it changes, every 30 seconds at most. Its sync code (kept as a test fixture, `test/fixtures/sync-v1.ts`) shows a viewer's file and a refusal's message as they are, and treats only 4401, 4403 and 4404 as final: any other close, 4426 included, has it reconnect every few seconds, so the room doesn't close on it.
  - **Every client that doesn't download gets the same bound, in either form** (`rooms/socket-snapshot.ts`): a tab from before 4b in a file still materialized (its conversion pending, refused for its instances' size, or turned off with `COMPACT_COPIES=off`), and a hello of version 2 without `download`. What's sent through the socket goes through one path: measured before anything is sent (stored characters in SQL, summed in pages that stop once past 8 MB rather than over the whole table on every such hello, then the file as it will be sent, stopping once past 8 MB), sent in chunks of at most 2,000 nodes and 1 MB, and past the bound the reload page as a viewer, its edits refused. The file is sent as presented only to a tab from before 4b in a compact file; otherwise as stored. A client that can download is sent a file through the socket only when it's under the same bound and 2,000 nodes. The reload page is welcomed at revision 0, and a client that can't download, at revision 0, in a file too large to send it, isn't caught up: the log would apply to the reload page. The seventh review found a tab from before 4b in a materialized file sent 2,000 stored rows at a time with no bound on bytes or in all (a file of 400 texts of 200,000 CJK characters ran a 128 MB heap out on the first page).
  - A client that lists no form the file has gets an error and the socket closes with 4426; the editor reloads the page then (once a minute at most). None does today: version 2 clients read both.
  - A version 1 tab open while the file converts becomes such a viewer right after the storage transaction that applies the conversion, with nothing awaited between: each socket records at welcome which forms it reads (`reads`), and one that can't read the file's form is never sent its changes (they're held back and the file is sent again), and its edits are refused telling it to reload. The same holds after an import in another form.
  - The room records each socket's form at welcome. Once the file has changed form, that socket's edits that touch no copy layer, instance, main or override record (and set none of their properties) apply as they are: a page renamed, a layer on a screen moved. The rest are refused (`format`), and the client is told to load the file again. The editor's sync sends `Doc.lastStoredOps`, and undoes its pending edits exactly with the stored inverse when rebasing; a remote change is applied as stored. Once an edit is sent, its stored operations are fixed: rebasing applies it again as it was sent (`applyStored`), exactly as the room will apply it, so what the client shows for it is what the room stores. Only an edit not sent yet is stored again against the document as it is (a copy's value equal to its main's again stores no record). Before the sixth review a sent edit was stored again too: a copy set to 200 while another client set its main to 200 dropped the record on the client while the room kept it, and the client and the room disagreed once the main changed again. Pending edits that can't apply after the file changed form (a copy's old id) are dropped with a notice. Ids pending edits hold in values (a reading order, a prototype destination, a flow's start) are found in the new form first (`packages/editor/src/form-change.ts`), as the converter renames them: a copy is the layer under its parent (found the same way) that copies what it copies (its `mirrors`, found the same way). That works both ways, to derived ids after a conversion and back after a rollback, and keeps the ids of a detached instance's layers. An edit holding an id that can't be found (its copy is gone), or naming something other than a layer (a style, a variable) the file doesn't have, is dropped with the same notice, as the room refuses it from a client in the old form (`#fromOldForm`), and never sent with an id the file doesn't have. A welcome makes every edit the room hasn't applied unsent again, so after a change of form (always loaded after a welcome) the edits replayed are new ones, which the room applies as sent: what the client applies is what the room applies. An edit sent in the old form and applied by the room has been translated by the room with the conversion's map, or renamed by the conversion itself, and comes back in the file. Were one still sent at the change, it would be applied translated the same way, or left unapplied for the room to refuse. The seventh review found a reading order of two copies replayed with their old ids: the room took it (a reading order's ids are checked for their form, not that they're there), and the order fell back to layout order.
- **A main containing an instance of itself** (directly, or through other mains: A holds an instance of B, which holds one of A) would present itself without end. The editor never made one (`wouldCycle`), but the model took such operations from any client. Now `applyTransaction` and `applyOp` refuse a transaction that would leave one (`cycle`: "A component can't contain an instance of itself, directly or through other components."), on every path: a create of an instance or a record swapping a copy, `instanceOf` set, a move, `isComponent` set. It's checked on what the whole transaction leaves, not after each operation: a restore creates the version's layers before it deletes the file's, so it can pass through a loop on its way to a file without one. Only what the operations touched is looked at: the mains around each node they touched, and the mains named at or under it, followed through what each main contains. The room asks that in SQL (`rooms/instance-cycles.ts`, through `SqlNodeStore.instanceCycle`): it follows which main each frame or record names and never parses a layer's other values, so a main of any size is checked without being read into memory. It keeps the nodes a storage transaction touched in a table (`cycle_check`) and checks them once its last chunk has applied, so a restore or a merge of any size holds none of them in memory either. Held operations (a client's rebase, a failed transaction's rollback, the editor's own rollback) aren't checked, since they put back what was there; the room checks every transaction it commits, held or not (restores, merges and updates included), so a client's rebase only ever follows what the room took. A file that already holds one (written before) is presented without looping: `CopyView` works out which mains contain themselves (strongly connected components over what each main's layers name) and builds their instances, and copies swapped to them, with no layers. Converting such a file detaches those instances first, keeping their stored layers and the look they had ("its component contains an instance of itself"); the rest converts as ever.
- **What the room checks in a compact file.** Override records as edits are (under an instance root, the id their path derives), as before; and, once each storage transaction's operations have applied, that they left no stored layer under an instance of a live main, and that a transaction that removes a main leaves every instance of it showing exactly what it showed (`rooms/main-removal.ts`).
  - **Removing a main** is anything after which a component's main isn't one: deleting it or something it's in, un-making it a component, moving it into an instance. The editor stores each instance's layers as they show before it removes a main; a client whose view is behind (another tab added a layer to the main, or changed its fill, since) stores what it saw, and the room must refuse that, or an acknowledged edit is lost. So, inside the transaction's storage transaction, the room builds what each affected instance shows before the operations apply and again after (the model's `CopyView`, as the editor builds it), hashes both, and refuses (`conflict`, 409 over HTTP) when they differ: "Removing the component “Card” would change how its instance “Card” looks, so nothing was changed. If someone just changed that instance or the component, try again; otherwise detach the instance first." The editor shows it and undoes its change; caught up, the same deletion stores the instance as it shows now, and is taken.
  - What's compared is the look: each layer's type, its place among its siblings and its values (a missing value equal to its default), in drawing order. Not ids, not the values that link a copy to its main (`mirrors`, `overrides`, `unset`), not an instance root's own placement (root-local values, never its main's). So an instance that stores `unset: ["fills"]` under a red main, stored by the editor without `unset` and without fills, shows the same and is taken.
  - Which instances: the main's (stored roots, and instances with a copy swapped to it), and the instances with override records of any main holding one of those, however deep. Storing a nested instance's layers gives them other derived ids (their path goes through the stored instance now, not the main's copy), and a record names its layer by id: an override inside an instance of a main holding the removed main's instance would be lost. The editor's own deletion does that today (see Consequences); the room refuses it, and detaching that instance first lets it through. An instance without records shows its main exactly, which is checked through the instances inside it.
  - When the mains a transaction removes aren't known before it applies (a restore, a merge, an update produce their operations as they go), each operation names the mains it may remove; at the end, those that aren't mains any more are what it removed, and if their instances weren't looked at first, the storage transaction is rolled back and run again, looking first (at most three times). An edit's deletes and un-makings are looked at before it applies, so it runs once. Instances inside what the transaction deletes aren't built (and if one is there after all, it's run again, looking at everything).
  - Bounded as it's built: one `BuildBudget` covers the check, before and after, charged for every copy built, every node presented and every row the room's store parses and keeps while it checks (`BUILD_HELD_BYTES`), and for every layer built in all (`REMOVAL_CHECK_LAYERS`, 400,000). Each instance lets go of what it read and built (its records and their values most of all) before the next is looked at. An instance that can't be built within the budget even with nothing else held, or instances too many to build, refuse the removal, saying the instance is too large to check: detach it first, or keep the component. Each instance is also measured in SQL first, under the conversion's limits (`MAX_INSTANCE_LAYERS`, `MAX_INSTANCE_BUILT`, `MAX_INSTANCE_BYTES`): a cheap first filter, not what safety rests on.
  - What grows with the file is kept in SQL, in tables of the check's own (`REMOVAL_SCHEMA`), emptied when a storage transaction starts it: the mains noted, the instances affected (found round by round with one pass over the file each, through the mains holding them), which ones are under what's deleted, and what each showed. They're counted before any is built, an instance counting a layer at least, so removing a main of 700,000 instances is refused as too many to check before anything is read (it had run a 128 MB heap out listing them). What a transaction run again carries over in memory is bounded: the removed mains that still have instances (more than `REMOVAL_CHECK_MAINS`, 10,000, refuses the change, saying to remove fewer at a time) and the targets of its deletes (up to `REMOVAL_DELETED_KEPT`, 50,000; past it, instances are looked at whether deleted or not).
  - Each instance left must not store layers under a live main, as before. This runs on every path that commits operations: edits, agent tools and their undo and redo, restores, merges and updates from main (a merge whose branch deletes a main that main has placed an instance of since is refused); a restore's or a merge's chunks are checked together, once. An import said to be compact may not store layers under an instance either, nor hold a component that contains an instance of itself: nothing converts it on the way in, so it's refused, naming the component (`checkStaged`'s `cycles`). We chose refusing over detaching: no importer makes one (Figma and Penpot don't allow it, and the browser's converter detaches one), so only a client writing the compact form itself can send it, and it's told what's wrong. An import that comes materialized is converted, which detaches such instances, keeping their look. A branch or a duplicate keeps what its file held, as the file presents it. A materialized file still refuses records.
- **Snapshots** say how they store copies in their header (`"copies":"compact"`; missing means materialized). A version, a branch's base or another file's nodes read into a compact room in the materialized form are converted as they're read (`compactTable`, the same steps, all at once on a table nobody edits), so restoring, merging and updating from main work across the conversion. A restore, a merge or an update awaits (saving a restore point, writing a branch's new base), and the file may convert meanwhile: what it read is brought to the file's form again after the last await, right before it works out what to commit. A materialized room can't read compact snapshots; it says so (conversion off, or the file not converted yet).
- **Downloads** (decision 0026, item 9) give a client exactly what the socket would: the stored form, the snapshot's header saying which. A download of the file as it is says the form of the copy it reads (the shared copy keeps it with its revision; a change of form is a revision of its own, so one revision has one form). A download from the latest saved version is offered only when the log reaches back to it (`#canReplayFrom`), and every change of form (a conversion, a restore under `COMPACT_COPIES=off`, an import in another form) moves `catchup_from` past it: so "Before compact copies", or any version saved in the form before, is never sent to a client welcomed in the new one, which gets the file as it is. The editor checks it anyway: a download whose header says another form than the welcome did isn't loaded, and is asked for again after the usual wait, as a failed download is (the room sends a resync when a file changes form, so a new welcome follows). A tab from before compact copies never says it can download; a hello of version 1 with `download` is treated as one without. The size that decides a download is of what the room stores, so a kit that converts may go back to coming through the socket. Tests: `compact-download.test.ts`, three ways in to one document (socket, saved version plus replay, the file as it is) and after the rollback.
- **Branches** copy their main's form. A branch made before its main converted has a materialized base; it's converted as it's read for review, merge and update. Ids are derived from root and path, so base, branch and main agree on every copy's id. Review in the browser compares stored forms, as main's room merges (so the changes and their keys are the same), converting a side that comes materialized with the room's converter (`compactByInstance`), and names a record by the layer it's for.
- **Libraries.** What a publish offers is counted in SQL before any row is read (each main, or the set it's a variant of: `componentAssets`), and past 2,000 refused; under it, only those rows are read, never every variant's. Publishing hashes components as presented (a `PresentedReader` over the frozen copy, an instance at a time), so a hash still changes exactly when what a component draws does. It does change once, at conversion, for components that contain instances: the hash includes the ids of the layers a component draws, and its copies' ids change from random to derived. The first publish after a library file converts lists those components as changed, and taking the update changes nothing anyone sees. Keeping the old hashes would mean keeping every copy's old id for good (about 50 bytes a copy layer, more than the compact file itself for a kit). A file using a library loads the publish in its own form, so copies inserted from it are named as it names them (4a's `copyNamer`, compact on both sides).
- **One converter.** Every path that turns the materialized form into the compact one uses `InstanceConverter`: the room over SQL, and `compactByInstance` in memory (browser imports, branch review, and `Doc.reset` and `Editor.loadStatic`, which show a saved version, a branch's main or a library in the open file's form). 4a's one-pass `compact` is removed, so nothing can call it: the sixth review found history and library loading still using it, reversing the drawing order of siblings sharing a key and leaving prototype links on a removed copy's old id.
- **Imports** are converted once, before or in the room: the browser converts with `compactByInstance` before it sends parts when the file says it's compact (about a fifth to upload). That is the room's `InstanceConverter`, an instance at a time, each verified, ids layers hold renamed: what the room would store had it come materialized. It was `compact` before the fifth review, which left reading orders and prototype links naming copies' old ids and could reverse the drawing order of siblings sharing a key, and the room takes what's said to be compact as it is. We kept converting in the browser rather than sending everything materialized: the upload stays a fifth, and a large import isn't converted inside the room's commit request. It takes about twice as long as `compact` did (6 s against 3 s for a 200,000-layer kit, in Node) and says so at the commit (`copies: "compact"`); the room converts at the commit whatever comes materialized (an older page, any other client), with the same converter. It can't tell the two apart by looking: in the compact form an instance equal to its main has no layers and no records, which in the materialized form is an empty instance (and is detached, keeping its look). The first e2e run found exactly that, with a browser-converted Penpot file. The one-request import (`POST /files/:id/import`, which new files from templates use) says it the same way, in its body. Override records sent without saying `compact` are refused rather than converted. A branch or a duplicate takes its source's form from the snapshot's header the same way. Records that arrive are checked at the commit as edits are.
- **Readers.** The MCP tools and library manifests read a compact file through `PresentedReader`: the model's `CopyView` over the room's table, an instance at a time, letting go of built copies past 20,000 between instances, or past half its `BuildBudget` (`BUILD_HELD_BYTES`); an instance that can't be built within the budget fails that read with `BuildTooLarge` rather than run the room out of memory (a comment pin's layer looked for that way is then pinned to the page). A copy layer asked for by id is found from its record, or by building instances in turn until it's there (slow on a large file, bounded in memory). What copies are built from is read within the budget: a parent's child ids are counted (or read with a limit of what the budget has room for) before they're read, and refused with `BuildTooLarge` past it; the search for mains that contain themselves charges its maps to the budget while it runs. Walks over a page or the whole file hold an iterator a level, never a level whole. Agent tools run the headless editor in the file's form, metered as it's built (decision 0026, item 8): its `CopyView` charges each copy layer to the editor's meter as it builds it (its slot by path length, and a cached presented copy its record and an object pointing at its main's values), so copies past the limit are refused as they're built, whatever their depth; the layer limit counts layers as presented. Thumbnails and exports are drawn in the browser from the presented document, so they're as before. Search (D1) indexes file names, not layers.

## How it's verified

- **Equivalence.** For any file in today's model, building every copy from the converted file gives back the same document, ids mapped. This is checked on the corpus at several sizes, the `.fig` and Penpot fixtures, the kit store's kits and the converted shadcn/ui pages, then property-tested with generated documents and edits. Applying an edit before or after conversion must give the same result, so the converter, the view and `apply` are held to one meaning.
- **The fuzzer** (`pnpm fuzz`) runs its edit sequences against both models and compares.
- **The scale benchmark** (decision 0027): editing a main is drawn within 100 ms however many copies it has, the stored file is about five times smaller for a kit, and loading takes no longer than before.

## Consequences

- A kit stores, syncs, snapshots and keeps in undo about a fifth of what it did, and editing a main costs the same with 10 copies or 10,000.
- Page loading (phase 3) becomes possible: a page needs its own records and the mains its instances use, and copies follow their mains on any page without being written to.
- The editor still holds every copy layer in memory once built; building them lazily, page by page, is phase 3's.
- New failure modes to guard: a record whose path no longer exists in its main (the main lost the layer; the record stays, unused, as overridden values do now, and is dropped when the instance is reset or detached); two clients creating the same record at once (the second transaction clashes and is refused, and the editor says so; an edit that reaches a client after the other's landed is stored again as a change to that record when it rebases); hash collisions (16 base-62 characters, about 95 bits; checked when a copy is built, and refused if two paths collide).
- This changes the file format, per file: the room's meta says which, the protocol says it at hello, and snapshots say it in their header. Files convert the first time their room loads after the deploy, each after a version to undo it with; `COMPACT_COPIES=off` stops that and, with it, restoring that version undoes it.
- A library's components that contain instances show as changed once, at the first publish after it converts (see Libraries above).
- Pending edits a client made in the old form when its file converted are refused, with a notice, when they touch copies (the rest apply; ids of copies they hold in values follow the copies); a client from before the deploy opens a converted file to view only, until it reloads. A client that can't download a file too large for the socket sees a page saying to reload, whatever the file's form.
- A file with an instance of more than 5,000 layers, one whose main presents more than 10,000, or one costing more than 8 MB with the mains it's built from (values, and 256 bytes a layer read or built), stays materialized: it converts by holding an instance whole, and one of 20,000 layers took about 80 MB doing so, more than a Durable Object can spare.
- Removing a main checks that its instances keep their look, building each before and after; a main whose instance is too large to check (the build budget, or the conversion's limits counted first), or whose instances show more than 400,000 layers in all, can't be removed in one change: its instances are detached first.
- What builds copies on the server (conversion, the removal check, the room's readers) is bounded by a budget charged as it builds, so a file of any shape stops it with a typed error rather than running the room out of memory. The costs are estimates measured in Node, not on Workers: if V8 on Workers holds more per slot, the budget's margin (24 MB of a 128 MB Durable Object) is what absorbs it.
- A main can't contain an instance of itself, through any client or path (checked on what each transaction leaves; a compact import holding one is refused); files that hold one from before present those instances empty, and converting detaches them, keeping what they show. A merge or restore that removes a main runs its storage transaction twice (the second time looking first).
- A tab from before compact copies sees a file larger than 8 MB as presented as one page saying to reload. Removing more than 10,000 components that still have instances in one change is refused; removing them a few thousand at a time works.
- **Bounded since by bytes (found by the sixth review's audit, left as on main then, each reached by ordinary actions on a legal file per the seventh review):** the agent tools are bounded by what the headless editor holds, counted as it's built and as it follows changes (decision 0026, item 8; an estimate in SQL, as first done, missed nested values and deep copies); a library's publish counts what it offers in SQL before reading any row; `SqlNodeStore`'s read cache keeps at most 8 MB, least recently used let go first (decision 0026, item 7). Each holds for either form.
- **Follow-up (accepted by the fourth review):** the editor, deleting a main that holds a nested instance, gives the nested instance's layers new ids, so an override an instance of another main kept on them would be lost; the room refuses that deletion, and the user detaches that instance first. Keeping those ids in the editor (re-keying the records, or deriving a stored nested instance's copies from its old path) is left to do.

# 0026. Large files on the server: imports in parts, snapshots as lines, differences in SQL

- Status: accepted
- Date: 2026-11-16
- Deciders: Ziyang (lead maintainer)

## Context

Real UI kits are 100,000 to 1,000,000 layers. The shadcn/ui Pro kit is about 503,000, some 225 MB of node JSON at 410 to 510 bytes a layer. Cloudflare gives a Worker or Durable Object 128 MB of memory per isolate, 32 MiB per RPC argument or return value, a 100 MB request body, and a CPU-time budget per request.

The FileRoom already kept a file's nodes in SQLite, one row each, and sent them to the editor in chunks. But every path that needed the whole file gathered it in memory, or into one message:

- **Import** was one request and one RPC call holding every node, checked on an in-memory copy (`MemoryStore`): capped at 24 MB, about 45,000 layers (decision 0025).
- **Versions** built one JSON string of the file, and reading one parsed it whole. **Restore** diffed two whole files in memory.
- **Branches** sent the main file over RPC (`snapshot()`) to make one, and review, merge and update read base, branch and main whole.
- **Libraries** and **MCP** read every node (`allNodes()`) to publish a manifest or answer a search. **Duplicating** a file did too.

## Decision

Nothing on the server holds a whole file, or sends one in one message. Each path works a page of rows (1,000) at a time, against tables in the room's own SQLite: a copy of the file frozen at one revision, a version read back from R2, another file's nodes, an import arriving in parts (`rooms/node-tables.ts`). Each has the columns of `nodes`, so rows move between them in SQL without passing through JavaScript.

1. **Imports come in parts.** `POST /files/:id/imports` begins one (only into an empty file), `POST …/imports/:importId/parts` sends about 4 MB of nodes at a time (12 MB at most), `POST …/commit` finishes it, `DELETE …/imports/:importId` gives up.
   - Each part's nodes are checked on their own as they arrive (id, order key, every property, `checkNode` in `@drawpane/model`) and kept in a table beside the file's, all or none of the part. A node sent twice is refused, and so is an override record (decision 0029: rooms don't store compact copies yet).
   - The import's totals are held to its limits as it goes: the part is kept, and the running count of nodes and bytes moved on, in one storage transaction, so a part that would take the import past either limit is refused and nothing of it stays. The commit checks the totals again. Bytes are UTF-8 bytes of each node's line of JSON, counted without copying it (`utf8Length`), as the request cap counts a body and as the browser counts the parts it sends: a character of CJK text is three bytes, an emoji four.
   - The commit checks how they fit together, in SQL: a page under the root, no id the file already has, every parent there and allowed to hold its child, and every node reachable from the root within 128 levels (levels are numbered a level at a time; what's left is inside itself or too deep). Then the file is filled from the table, and its starting page removed, in one storage transaction. Until then the file is as it was, and anyone opening it sees its empty page; a failed commit leaves it so.
   - The commit replaces the file as it was when the import began, so it's refused (409, nothing imported) when the file has changed since: someone opening the new file and renaming its page while the parts upload would otherwise lose that acknowledged edit. The begin notes the revision; any edit moves it on.
   - An import is one revision, not logged as operations. Clients behind it load the file rather than catch up: the room notes the import's revision, and a client from before it gets the file, not the log. The log before the import stays, for who edited what. An import nobody commits is thrown away after an hour, or when another begins.
   - A copy of a file this server already holds (a branch, a duplicate) goes through the same staging, without the import limits and at any depth, since a file can grow past what one import brings.
   - One import takes at most 1,000,000 nodes in 640 MB of JSON (`MAX_IMPORT_NODES`, `MAX_IMPORT_BYTES`). The browser's `saveImport` sends the parts, serializing each node once as its part goes; the .fig dialog aims for 1,000,000 estimated layers (`FILE_LAYERS`) and lists pages to choose only beyond that. `POST /files/:id/import` stays, for an import of one part.
2. **Snapshots are lines of JSON, written and read as streams.** Version 2 is a header line, then a node per line, gzipped. A version is written from a copy of the nodes made in SQL at one revision (so edits while it uploads don't show), read a page at a time, gzipped as a stream, and uploaded to R2 in 8 MiB parts (a multipart upload; one put when it's smaller). Reading streams too. Version 1 snapshots (one JSON object) stay readable, as a stream: a small scanner hands back each node's text from the `nodes` array without parsing the whole. The API sends a version's stored bytes as they are; the browser reads either (`parseSnapshot`).
3. **Restore works in SQL.** The version is read into a table, its levels numbered (as deep as they go: a file may hold layers past 128 levels, see below), and compared with the file a page at a time, top-down (a page bounded by the characters of both sides' values as well as by rows: `boundedPages`), with the same per-node comparison the editor's restore uses (`restoreNodeOps`); then the topmost of the file's nodes the version lacks are deleted. A node byte-for-byte the same is skipped without parsing. A version with a node that can't be numbered (inside itself, or under a parent the version lacks) is refused with nothing changed, never taken as lacking that node, which would delete it from the file; nodes of a kind this schema doesn't know are left out with what they hold, as before. An operation the model refuses (a layer placed past 128 levels) refuses the whole restore too. The operations are committed in chunks of about 1 MB, each a logged revision, all in one storage transaction; everyone sees them arrive, or is asked to load the file again when they're more than a broadcast carries.
4. **Branches stream room to room.** Making one: main's room writes its base to R2 from a frozen copy, and the branch's room fills itself from that. Review: the Worker streams base, branch and main as lines of JSON, each after a line naming it. Merge: main's room reads the base from R2 and the branch as a snapshot stream from the branch's room (Workers RPC carries streams), each into a table, counts the changes and the conflicts nobody decided (a page of the branch joined with base and main, bounded by the characters of the three sides' values as well as by rows), and applies the chosen ones with the model's per-node comparisons (`addedChange`, `changedFields`, `editedSince`), in the order `mergeOps` gives: added parents first, changed fields, deletions. Deletions are planned against main as the merge's moves leave it: one inside another being deleted (main moved it there since the base) goes with it, rather than being deleted twice. It all lands in one storage transaction, or none of it does.
   - Updating from main is the same in the branch's room, which takes main as read as its new base, the two together or neither: main as read is written to R2 first under a key of its own (`files/<branch>/branch-bases/<revision>-<random>.json.gz`), then the branch's changes and the room's pointer to its base are committed in one storage transaction. A failed write or commit leaves the branch and its base as they were, so trying again works. Updates of a branch run one at a time, and one bringing main from before the current base changes nothing. The base it replaced is deleted by the room's alarm an hour later, since a review or merge that read the pointer may still be reading it. Review and merge ask the branch's room for its nodes and its base's key in one call (`exportBranch`).
5. **Libraries and MCP ask the room.** Publishing freezes a copy, reads what it offers from that copy through a reader that fetches rows as the hashing asks (keeping at most 10,000) and finds components by a query, counted in SQL first: past `MAX_LIBRARY_ASSETS` (2,000) the publish is refused before any row is read, and under it what's read is each component's or set's row, never every variant's (`componentAssets`), and saves the version from the same copy. A component's hash is taken as its layers are walked, a line at a time (cyrb53 fed piece by piece gives the hash of the lines joined, so earlier publishes compare equal), and the walk reads a node's children a page at a time, holding only the path down to where it is. A level the walk has gone down from keeps its page's ids and where the next page starts, not its rows: the rows go to the reader's cache as they're read (at most 10,000 of them and 8 MB of their properties as V8 holds them, a byte a character and two past Latin-1, the oldest let go first), and a node is read again on its own when the walk comes back to it after the cache has let it go. So memory grows with depth by a page of ids a level, not a page of rows: a file 128 levels deep with a thousand layers of 1,200 characters at every level (126,002 layers) is hashed, and searched by MCP, with the heap capped at 64 MB; before, the suspended pages held nearly the whole file (406 MB hashing it, uncapped). Components are found at any depth: a component's place in the file is walked up to its page however far that is (stopping if it comes round again), so one under more than 128 levels, which a file may hold (see 6), is published as the in-memory reader finds it. The MCP read tools are answered by the room from SQLite the same way: children a page at a time, counted by a query, never gathered into one list, and a search's walk holds ids on its way down and reads a node when it reaches it (a chain of 126 frames of about 1 MB of properties each is searched with the heap capped at 64 MB); `get_node` lists a layer's first 500 children and counts the rest. Duplicating a file streams it room to room.
6. **No edit takes anything deeper past 128 levels; what was already deeper stays.** A move checked only where the moved layer lands, so a valid move could take what it holds past 128 levels, and files hold such layers now. One rule settles it, in the model's `applyOp`, so the editor, the room and agents apply it alike: an operation may not make anything deeper than 128 levels unless it was already that deep.
   - A move is refused only when it takes the layer deeper and the deepest layer it carries ends up past 128 (on the server, one SQL query, `deeperThan`). Reordering a layer where it is, or moving one shallower, is allowed however deep it is, so a file holding deeper layers can still be tidied.
   - A new layer is refused past 128 levels. Undoing the deletion of one there is an edit like any other, so it's refused too; restoring a version brings it back.
   - Levels are counted up to the root as far as they go, never stopping at 128, and a walk that comes round again (a store holding a cycle) ends as a `cycle` refusal rather than looping.
   - What puts back layers a file held is applied as deep as they stood (`held` in `ApplyOptions`): a restore (a replay of a version the server holds), a transaction's own rollback, the editor undoing its unacknowledged edits to rebase, and a change the room accepted arriving at the editor or the agent engine. Branching and duplicating copy the file through staging at any depth. A merge and an update from main follow the ordinary rule: they combine two files' changes into a tree neither held (main moves an empty group to 128 levels down while the branch puts a layer in it), so a result past the limit is refused as a conflict and neither file changes. Imports from outside keep the limit.
7. **Deleting without reading.** A delete nobody needs back (a restore, a merge, an ordinary edit) removes the subtree in one SQL statement instead of collecting it to undo with (`removeTree`).
   - **An edit holds a few rows.** The store's read cache (`SqlNodeStore`) keeps at most 8 MB (`STORE_CACHE_BYTES`, counting two bytes a character of a row's JSON), letting the least recently used go first. Writes go to SQLite as they're made, so a row let go of is read again when next asked for, and a transaction stays all or nothing (its storage transaction, and the model's rollback reading what it needs again). It had kept every row a chunk of operations read until the chunk applied: dragging a selection of 400 texts of 200,000 CJK characters (18 KB of setters) ran a 128 MB heap out.
8. **Agents keep a size limit, by layers and by bytes.** The headless editor (decision 0021) holds the whole file in memory, so a file is admitted by what it would hold, worked out in SQL before a row is read (`rooms/agent-admission.ts`): at most 50,000 layers as presented (`AGENT_MAX_NODES`), and an estimate of at most 48 MB (`AGENT_MAX_HELD`). The estimate is 320 bytes a stored node (`AGENT_LAYER_BYTES`), 760 a copy the editor builds (`AGENT_COPY_BYTES`, compact copies), and the UTF-8 bytes of the stored values, summed in pages that stop once past the bound (`sumPast`).
   - **Measured** in Node with the stand-in text measurer (`test-node/agent-bounds.test.ts` holds the shapes): the built editor held about a heap byte per UTF-8 byte of long text (1.00 for ASCII and emoji, 0.67 for CJK, which V8 keeps two bytes a character and UTF-8 three); 524 bytes a rectangle and 624 a text of 300 characters, values included (under 320 beyond their UTF-8 bytes); 707 bytes a copy built from its main. Building peaked at 1.4 to 1.5 times what it then held, sampled uncapped. So 48 MB leaves a 128 MB room about 25 MB beside a build's peak and the 17 MB it starts with. A 50,000-layer kit (about 450 bytes of JSON a layer) comes to about 38 MB, and is admitted as before.
   - The largest file of long texts admitted (83 texts of 200,000 CJK characters, 50 MB of UTF-8) builds, and is read whole by `get_jsx`, at a peak of 95.5 MB with the heap capped at 128 MB. Counting layers alone had admitted 401 layers holding 240 MB of text (the seventh review of #163), and an ordinary `get_jsx` ran the room out of memory reading them.
   - The warm editor counts what it follows (twice the characters of each transaction's JSON, and a layer per create) and lets itself go past the bound, so a file that grew while it was warm is measured again before it's built, and a call whose file grew while it awaited its fonts is refused rather than built. The read tools work at any size.
9. **Opening a large file downloads it.** The room used to send a file opened afresh through its socket, every chunk at once. A socket has no backpressure, so the room held all of it: a 503,000-layer kit (339 MB) took the room past 128 MB, it was reset, and the editor, having taken the welcome's revision as its own, reconnected "caught up" to an empty document. Now a client says in its hello that it can download (`download: true`), and for a file of more than one snapshot chunk (`INLINE_SNAPSHOT_NODES`, 2,000 nodes) or of more than 8 million characters of properties (a text layer may hold 200,000), counted in SQL over at most 2,001 rows, the welcome's mode is `download`, with a ticket: a signed `{purpose: "document", fid, uid, revn, exp}`, good for five minutes, minted only for someone the room let in. Each download checks again that `uid` still has the file (on its team, or, for a guest, the prototype link still on), so a ticket doesn't outlast access. `GET /api/files/:id/document?ticket=` streams version 2 snapshot text, gzipped: the latest saved version from R2 when the log holds every transaction since it (none before the last import, at most 8 MB of them), which the room sends through the socket right after the welcome; otherwise, and when that version has gone, the file as it is, copied aside in the room (`exportDocument`): downloads of one revision share one copy, dropped when the last ends, so many people opening a large file at once make one copy, not one each. Guests get only the latter. Pages of rows are bounded by characters as well as rows (`tablePages`, 4 million characters; `boundedPages` for a page joined with other tables' values, as a restore's and a merge's are), so a page of large layers stays small wherever the server reads one. The browser parses the download a line at a time as it arrives (`readSnapshotStream`), buffers transactions meanwhile, and applies those after the snapshot's revision; it takes a revision as its own only once the file is in, so a connection lost while loading leaves it where it was. A failed download, or one that won't load, is asked for again, waiting longer each time. While the file loads again (a resync, a snapshot, a download), nothing moves the client's revision, neither an ack nor a change, and changes buffer; a client has one hello out at a time, since two welcomes would each reset its unconfirmed edits, the second from before edits sent after the first. A client that doesn't say it can download (an older tab, a headless client) is sent the file through the socket as before.

## Consequences

- **Measured** on a file of 505,010 layers (213 MB of JSON, 78 MB gzipped as a version 2 snapshot), running the room's code in Node 26 on this VM with the V8 heap capped (`pnpm --filter @drawpane/worker memory`). Every path finishes with the heap capped at 128 MB, and again at 64 MB. Peak heap is sampled as the path runs, so it includes garbage not yet collected; "buffers" are ArrayBuffers (gzip and R2 parts), which count toward a Durable Object's memory too; RSS includes SQLite's page cache and the test runner. Times at the 128 MB cap:

  | Path | Time | Peak heap (128 MB cap) | Peak heap (64 MB cap) | Peak buffers |
  | --- | --- | --- | --- | --- |
  | Import: 4 MB parts parsed and checked, then the commit's checks and fill | 40 s | 95 MB | 70 MB | 0 MB |
  | Save a version (frozen copy, gzip stream, 8 MiB R2 parts) | 19 s | 32 MB | 16 MB | 30 MB |
  | Restore a version (read back into a table, compared in SQL) | 55 s | 91 MB | 67 MB | 12 MB |
  | Restore a version 1 snapshot (read as a stream) | 44 s | 87 MB | 58 MB | 11 MB |
  | Make a branch (main's base written to R2) | 16 s | 39 MB | 17 MB | 54 MB |
  | Merge (base from R2, branch streamed in, compared in SQL) | 68 s | 87 MB | 58 MB | 11 MB |
  | Review (three files streamed as lines) | 6 s | 65 MB | 25 MB | 34 MB |
  | Duplicate (room to room stream) | 26 s | 52 MB | 25 MB | 10 MB |
  | Library manifest (200 components found by query and hashed) | 7 s | 56 MB | 56 MB | 0 MB |
  | Library manifest, one component holding every layer (walked and hashed as it goes) | 36 s | 96 MB | 69 MB | 0 MB |
  | MCP `find_nodes` over every layer | 12 s | 90 MB | 72 MB | 0 MB |
  | Library manifest of a comb: 126,002 layers 128 levels deep, 999 texts of 1,200 characters at each level | 17 s | 102 MB | 70 MB | 0 MB |
  | MCP `find_nodes` over that comb | 7 s | 98 MB | 68 MB | 0 MB |

  The heap before each path was 15 to 17 MB (the runner, zod, the model). The component holding every layer ran out of the 128 MB heap before its hash was taken as it walks (it gathered the layers, then their lines joined). Before this, the same file couldn't be imported at all (24 MB per import), a version of it would have been one 213 MB string, and restoring or merging it held two or three copies as objects. The comb (`test-node/comb.test.ts`) ran out of the 128 MB heap while each level the walk had gone down from kept its page of rows (406 MB hashing it, 536 MB for the manifest, 327 MB searching it, uncapped); now a level keeps its page's ids.
- **Rows of large values** (`test-node/room-bounds.test.ts`, `agent-bounds.test.ts`): a text layer may hold 200,000 characters, 600 KB stored for CJK, so a legal file of 401 layers holds 240 MB. Each of these ran a 128 MB heap out before its fix: the first three were found by the seventh review of #163, the rest by the audit after it. Peak heap, sampled as the path runs (garbage included: rows parsed and let go of fill the heap until V8 collects them):

  | Path | 128 MB cap | 64 MB cap |
  | --- | --- | --- |
  | Move 400 texts of 200,000 CJK characters in one transaction (store cache) | 90.5 MB | 61.0 MB |
  | The same, keeping the inverse (an agent's undo); and failing at its last operation, rolled back | 90.1 to 90.8 MB | 60.2 to 61.7 MB |
  | Agent tools on them: refused in SQL (from about 32 MB, the editor loaded) | 31.8 MB | 31.8 MB |
  | Publish 40,000 components with 2,000-character descriptions: refused as too many, counted first | 38.5 MB | 38.5 MB |
  | Publish them as 20 sets of variants: offered, every variant hashed | 98.7 MB (8.6 MB held after) | 65.6 MB (8.5 MB held after) |
  | Restore a version that changed every text | 100.9 MB | 59.3 MB |
  | Merge a branch that changed every text | 97.2 MB | 59.0 MB |
  | An agent's undo looking through 300 log rows of a text typed in (180 MB) | 81.8 MB | 48.4 MB |

  The 20 sets peak past the 64 MB cap by what new space holds (the cap is old space's); what's left once collected is the readers' caches. The size check for a client that can't download sums rows' lengths in pages that stop once past its bound (`sumPast`): checked by `rowsRead` in workerd, 20,000 rows of 2,000 characters read fewer than 8,000, where it read all 20,000 on every such hello (`test/socket-bound.test.ts`).
- The heaviest calls take tens of seconds of CPU here, past the 30 seconds a request gets by default, so the Worker's `limits.cpu_ms` is raised to 300,000 (five minutes, the most Cloudflare allows; it's billed as used). The installer carries it, as it does the rest of `wrangler.jsonc`.

- Every path stores the file once more while it works (a frozen copy, a version read back), as SQLite rows, dropped when done or, if a reader lets go, by the alarm within the hour. A room storing 225 MB of nodes needs that again for a while.
- The memory check runs the room's own code in Node (`pnpm --filter @drawpane/worker memory`, `test-node/`), against node:sqlite and a file-backed R2, because local workerd doesn't enforce 128 MB. It isn't part of `pnpm test`; `test/large-files.test.ts` runs the same paths through the real Worker and Durable Objects at 121,204 layers (40 MB of JSON), every run.
- Not measured on Cloudflare: whether a storage transaction of 500,000 inserted rows, or a commit's CPU time, stays inside a production Durable Object's limits. The import's commit and a large merge are the heaviest single calls.
- **End to end**, the shadcn/ui Pro kit's `.fig` imports whole through the browser (`E2E_LARGE_FIG=<path> npx playwright test e2e/large-fig.spec.ts`, against a local Worker): 88 pages and 503,378 layers in 13.7 minutes, sent as 60 parts (238 MB). Its first run found a converter bug the old budget had hidden: Figma lets a group be a mask and Drawpane doesn't, so the server refused the layer; such masks now come in unmasking, with a note.
- The browser still holds whole files where it reads or shows them: converting an import, opening a file, previewing a version, reviewing a branch. Importing the kit, Chrome's renderer peaked at 6 GB on this VM (the .fig reader's passes and the converted nodes); it held, but a machine with 8 GB of memory may not.
